# SceneFlow 分寸账本改造方案（场景 → 职责主体）

> 版本：v1.0（2026-11-05）
> 状态：已定稿，待开工
> 前置讨论结论：SceneFlow 的病根不是 UI 也不是交互，是**资产位押错了**——押在"场景=冻结计划"上，本质是 n8n 存管道。本方案把资产位换到**分寸账本**：计划降级为缓存，账本（约束/先例/统计）成为唯一复利资产。
>
> 一句话定位：**第 N 次运行凭什么比第 1 次更好？——答得上来就是下一代 agent，答不上来就还是任务处理器。**

---

## 0. 设计铁律（四条，防止做歪）

1. **只结晶，不发明**——账本里每条约束必须有人的信号出处（打回原因/修改 diff/👎 原因），agent 永不自己发明约束。
2. **计划是缓存**——不投资 DAG 编辑器；重规划随时整个换掉计划，账本不动。
3. **置信度外生于账本**——只用统计（连续无干预通过次数、打回衰减），禁用模型自评。
4. **北极星指标 = 第 N 次人工介入次数**——所有功能最终服务于这条单调下降曲线。

---

## 1. 核心区分：教学 ≠ 分寸

不是所有人工修改都进账本。**判断标准：下次重规划，模型自己能不能想对？**

| 信号 | 能想对吗 | 归宿 |
|---|---|---|
| 闸1 改 goal 措辞（"帮我整理"→"生成"） | 能（更好的表述） | 只更新计划缓存 + gateStats.edits，**不入账本** |
| 闸2 改步骤 title/顺序 | 能（计划层） | 只更新 definition，**不入账本** |
| 闸3 换能力（"别用爬虫，用文件读取"） | **不能**（偏好） | 分寸 → pendingConfirm |
| 闸4 勾验收项 | **不能**（标准） | 分寸 → pendingConfirm（直接 checkable） |
| 工作模式改产出内容 | **不能**（最强分寸） | 分寸 → pendingConfirm |
| reject comment | **不能** | 分寸 → pendingConfirm |
| 👎+原因 | **不能** | 分寸 + rejected 事件 |

闸门5 签约清单**只展示分寸类候选**；教学类根本不出现。此区分不做好，账本三天被计划噪音灌满。

## 2. 全景数据流

```
信号源                    账本（唯一写入点）              行为改变
────────                  ──────────────                ────────
闸门 reject+原因   ──┐                                ┌─→ 置信度 ↓ / 闸门回全开
闸门 edit diff     ──┤    pendingConfirm 队列          ├─→ 重规划 prompt 注入
guide-run 纠正     ──┼──→ （闸门5签约后转 active）───→ ├─→ 产出自检 checklist
👍/👎+原因         ──┤    runStats/gateStats           ├─→ replay/replan 路由
产出编辑(最高优先) ──┤    inputPatterns                └─→ 干预曲线
沉默超时(10min)    ──┘    interventions
```

## 3. 账本数据模型（P0，src/scenario/ledger.ts）

```ts
const ConstraintOriginSchema = z.object({
  type: z.enum(["reject", "gate-edit", "feedback", "guide", "artifact-edit"]),
  text: z.string(),          // 人的原话或 diff 摘要，永远保留
  at: z.string(),
  runId: z.string().nullable(),
});

const ConstraintSchema = z.object({
  id: z.string(),                        // "c-" + nanoid(8)
  clause: z.string(),                    // 人可读条款："行动项必须带负责人和截止日"
  scope: z.enum(["goal", "step", "capability", "acceptance", "output"]),
  kind: z.enum(["advisory", "must_contain", "must_not_contain"]),
  pattern: z.string().nullable(),        // kind≠advisory 时的可执行判据（子串/正则）
  origin: ConstraintOriginSchema,
  confirmedAt: z.string().nullable(),    // null = pendingConfirm，闸门5签约后填
  hits: z.number().int().default(0),     // 自检拦下它的次数
  active: z.boolean().default(true),
  supersededBy: z.string().nullable(),   // 冲突裁决后指向胜者
});

export const ScenarioLedgerSchema = z.object({
  version: z.literal(1),
  constraints: z.array(ConstraintSchema).max(200),
  runStats: z.object({
    runs: z.number().int(),
    accepted: z.number().int(),          // 👍 或沉默超时
    rejected: z.number().int(),          // 👎 或 retry
    corrected: z.number().int(),         // guide/产出编辑
    consecutiveClean: z.number().int(),  // 连续 accepted 且零干预（仅有人值守运行推进）
  }),
  gateStats: z.record(z.string(), z.object({  // key: "1".."5"
    passes: z.number().int(), rejects: z.number().int(),
    edits: z.number().int(), lastEventAt: z.string(),
  })),
  inputPatterns: z.array(z.object({
    digest: z.string(), at: z.string(),
    outcome: z.enum(["accepted", "rejected", "corrected"]),
  })).max(50),
  interventions: z.array(z.object({
    runId: z.string(), at: z.string(),
    gatesAnswered: z.number().int(),     // 全开闸门数（抽查态展开也计）
    questionsAnswered: z.number().int(),
    correctionsGiven: z.number().int(),
    total: z.number().int(),
  })).max(200),
});
```

- `ScenarioRecord` 加 `ledger: ScenarioLedgerSchema.optional()`。
- 迁移走 `domains/migrate.ts` 的幂等模式：老记录 `ledger = {version:1, constraints:[], runStats:{runs:successCount+failCount, accepted:successCount, rejected:failCount, corrected:0, consecutiveClean: min(successCount,1)}, gateStats:{}, inputPatterns:[], interventions:[]}`。
- **注意**：consecutiveClean 迁移初值 `min(successCount,1)`——老成功次数无干预记录，不可信，宁可保守。
- 不变量：迁移幂等（跑三次结果一致）、无账本场景全部现有行为不变（549 测试绿是底线）。

### 写入原子性（所有 ledger 变更唯一通道）

```ts
// library.ts
async updateLedger(id: string, fn: (l: ScenarioLedger) => ScenarioLedger): Promise<void>
// 内部：store 锁内 read→fn→validate→write，连带 .bak
```

禁止任何调用方直接改 `record.ledger`。闸门决策、feedback、Edit-to-Accept、体检降档全部走此入口。测试：并发 20 次 updateLedger 无丢更新。

## 4. 条款生成规则（分闸门写死，无 LLM 参与）

**原则：clause 文本 = 人的原话（轻模板化），kind/scope 由信号类型机械决定。**

| 信号 | scope | kind | clause 生成 |
|---|---|---|---|
| 闸3 reject/换能力 | capability | advisory | `步骤「{nodeTitle}」使用「{chosenCap}」`（comment 非空则追加原话） |
| 闸4 勾选变化 | acceptance | must_contain | `验收必须包含：{勾选项中文名}`，pattern=null（走 judge） |
| reject comment（闸1-5） | 1→goal/2→step/3→capability/4→acceptance/5→output | advisory | **原话即条款**，仅去掉"不对/重新"否定前缀 |
| 👎+原因 | output | advisory | 原话即条款 |
| guide-run 文本 | output | advisory | 原话即条款 |
| 产出编辑 diff | output | advisory | `产出中「{锚}」应为「{新值摘要}」`（见 §7 outputdiff） |

**质量门槛（防垃圾条款）**：comment 去标点后 <4 字或全是否定/语气词（"不对""不行""重做"）→ 只记事件，不生成提案。词表硬编码。

**must_contain 机械升级规则**：同类产出编辑命中 ≥2 次且新值含稳定子串（日期格式/字段名）→ 升级 `kind=must_contain, pattern=子串`。首次全是 advisory 走 judge；机械判据是被验证两次后**长出来**的。

## 5. 置信度引擎（src/scenario/confidence.ts）

```ts
const TAU_DAYS = 14;          // 事件半衰期
decay(at) = Math.exp(-daysSince(at) / TAU_DAYS);

export function confidence(ledger): number {
  const s = ledger.runStats;
  const recentRejects = countEvents(ledger, ["rejected"], 30);   // 30 天窗
  const recentCorr = countEvents(ledger, ["corrected"], 30);
  return 1.0 * s.consecutiveClean
       - 0.8 * recentRejects
       - 0.5 * recentCorr;
}
export type Tier = "replay" | "spot" | "full";
export function tierOf(c: number): Tier {
  if (c >= 3) return "replay";   // R_THR
  if (c >= 1) return "spot";     // S_THR
  return "full";
}
```

更新时机（run 收尾一个事务，原子）：
- accepted：`consecutiveClean++`, `accepted++`
- rejected/corrected：`consecutiveClean = 0`，对应计数 `++`
- **consecutiveClean 只由有人值守的运行推进**（见 §9 无人值守规则）

## 6. 双路路由 + digest + 强制体检

```ts
// src/scenario/digest.ts
export function inputDigest(requirement: string, slots: Record<string,string>): string {
  // goal 不进 digest（goal 变 = match 层已换场景）
  const keys = Object.keys(slots).sort();
  const norm = (v:string) => v.trim().toLowerCase()
    .replace(/[\uFF01-\uFF5E]/g, c => String.fromCharCode(c.charCodeAt(0)-0xFEE0))
    .replace(/\s+/g," ");
  return sha1(keys.map(k => `${k}:${norm(slots[k])}`).join("|"));
}
```

路由（match 命中后、执行前）：

```
tier=replay 且 digest 命中 inputPatterns(近10条 accepted)
且 replayCount % 10 !== 0                    → 重放 definition（注入模板A）
否则                                          → 重规划（注入模板A+B）
degraded 场景                                 → 强制重规划（禁重放）
重规划失败（规划器异常）                        → 回退重放缓存计划 + 交付卡标注"旧计划兜底"
```

**强制体检**：每场景每 10 次重放强制 1 次重规划。体检 run 若与重放产出 diff 显著超阈值 → 自动降一档 tier + 场景卡标注"世界可能已变化"。防静默漂移的复利系统防僵化机制。

**重放不豁免自检**——只豁免规划。

无 slots 场景 digest 恒定值，永远命中——符合语义（drift 由 goal/match 层管）。

## 7. 产出编辑监控：Edit-to-Accept（最强信号）

现状缺口：产品里用户没有"改 agent 产出"的通道（只有复制/重试），最强信号无源可采。

### 交互

```
终态产出卡 → [修改] 按钮 → textarea 就地展开（原文预填）
  → 保存时原子三件事：
     ① diff(原文, 改文) → 结构化改动块 → pendingConfirm 提案
     ② runStats: corrected++, consecutiveClean=0
     ③ interventions 记 1 次纠正
  → 显示改后版本，卡片角标"已由你修订"
```

### 结构化 diff（src/panel/outputdiff.ts）

行级 LCS 找改动块 → 每块归入四类：

```ts
type EditKind = "removed" | "reworded" | "added" | "format";
type EditBlock = {
  kind: EditKind;
  anchor: string;      // 定位锚：改动块上方最近的标题/句首，≤40字
  before?: string;     // 原片段，≤200字
  after?: string;      // 新片段，≤200字
};
```

| kind | 生成的条款候选 |
|---|---|
| removed | `must_not_contain` 候选："不要 {锚} 部分" |
| reworded | advisory："{锚} 的表述应为「{after 摘要}」" |
| added | `must_contain` 候选（两次命中升级规则） |
| format（顺序/标点/markdown 层级） | format 偏好桶，独立 scope，不与内容条款混 |

尺寸控制：每块截断 200 字、每 run 最多 5 块入提案、原文不落账本只落锚+块。

### 其余编辑点位

| 点位 | 处理 |
|---|---|
| 进度卡步骤行编辑（redo-single seed） | 指令措辞变=缓存更新；同步骤类型反复改写第二次命中 → 升级 capability 偏好提案 |
| artifact 编辑（version-artifact） | 新版本创建时 diff 旧版 → 同一 outputdiff 算法 → 提案 |
| 用户改自己消息重跑 | **不记 rejected**（需求修正≠agent 的错），只记 interventions + 新 run |
| 复制/下载 | `copied` 事件，不动置信度，留给降级判定当辅助证据 |

### 竞态与幂等

| 情况 | 处理 |
|---|---|
| 沉默窗内发生编辑 | 撤销 pending 沉默 accepted，改记 corrected——先到先得，编辑优先 |
| 同 runId 编辑多次 | 合并取最终 diff，corrected 只计 1 次 |
| 编辑后又点 👍 | 忽略 👍，角标保持"已修订" |
| 连续快速编辑 | debounce 1.5s 提交 diff |

## 9. 无人值守运行规则（定时/长程）

夜里跑的场景没人看，"沉默"含义完全不同。规则一条：

**consecutiveClean 只由有人值守的运行推进。** 定时/长程运行记 `runs++`、可记 rejected（失败自证），但沉默**不记 accepted**——没人看过的成功不构成验证，否则夜跑 30 天的坏场景会攒出 replay 匀放大 30 倍错误。

实现：`recordRunOutcome(runId, {attended: boolean})`，launch.ts 按触发源（用户会话 vs tasks.json 调度）打标。

## 10. 产出自检时序（src/panel/selfcheck.ts）

```
执行完成 → collect active constraints (confirmedAt≠null, active, 未被 supersede)
  ├─ 空 ─→ 直接交付
  ├─ 机械项(kind=must_contain) → 规则判：子串/正则
  │     违规 k 条 → hits++, 进入修复
  └─ judge（便宜模型一次调用，模板C）：
      只对 advisory 与机械未覆盖项，输出逐条 pass/fail
  修复：违规条款注入修正提示 → 执行模型重产出（≤1 次）→ 复检（只检违规项）
  仍违规 → 带标注交付（卡片黄标"未满足：{clause}"），run 标 suspected，
          不更新 consecutiveClean，不写 accepted
```

成本上限：每 run 自检最多 2 次模型调用（judge 1 + 修复后复检 1）。

## 11. Prompt 模板三件套（写死）

**模板 A · 约束注入（重放/重规划共用）：**
```
【该场景已积累的工作约束——必须全部满足】
1. [c-x1] 行动项必须带负责人和截止日
2. [c-x2] 该步骤使用文件读取而非爬虫
若计划确实无法满足某条，在产出中显式标注 [c-编号] 及原因，禁止静默违反。
```

**模板 B · 先例注入（仅重规划，最近 2 条、digest 最相似优先）：**
```
【历史被接受的产出示例（参考形态，勿复制内容）】
--- 先例 #{n}（{date}）摘要 ---\n{digest ≤300字}
```

**模板 C · 自检 judge：**
```
你是验收检查员。逐条判定【产出】是否满足【条款】，只依据字面。
输出 JSON 数组，每条：{"id":"c-xx","pass":true/false,"reason":"≤20字"}
判定从严：无法确认满足即 false。
【条款】… 【产出】…
```

## 12. 端到端时序磁带（一次有人值守运行，集成测试骨架）

```
00 用户发需求 ──────────────────────→ digest(requirement, slots) 计算
01 match() 命中场景 s ──────────────→ 读 ledger
02 路由判定 ────────────────────────→ tier × digest 命中 × replayCount%10
                                      ├─ 重放：模板A → 执行 definition
                                      └─ 重规划：模板A+B → planner
03 执行中 ──────────────────────────→ guide-run 到达 ⇒ corrected+提案
04 产出落地 ────────────────────────→ 自检：机械→judge→修复≤1轮
05 交付卡渲染 ──────────────────────→ 黄标(未满足) / 角标(已修订)
06 [用户反应窗 10min，先到先得]
   a. 👎+原因 → rejected+提案，断连胜
   b. Edit-to-Accept → corrected+diff提案（优先级最高）
   c. 👍 → accepted
   d. guide → corrected+提案
   e. 沉默超时 → accepted(弱)——被 a/b/d 撤销
07 recordRunOutcome（事务）──────────→ runStats/gateStats/inputPatterns/interventions
08 快照广播 ────────────────────────→ sparkline/曲线刷新
```

## 13. 与 Memory 系统的边界

| | Memory | Ledger |
|---|---|---|
| 存什么 | 发生了什么（叙事） | 什么被验证过（结构） |
| 给谁用 | LLM 上下文垫料 | 行为门控（路由/闸门/自检） |
| 形态 | markdown 叙事 | 结构化条款+统计 |

唯一交点：条款签约时同步写一行 memory（`[ledger] 新增约束 c-x1: …`）。反向禁止：memory 内容永不自动变条款。

## 14. 闸门5 签约面 UI

```
┌ 保存这个场景 ──────────────────────────┐
│ 本轮构建你教了它 N 条分寸：              │
│ ☑ [偏好] 步骤「获取数据」用文件读取      │  ← 分寸类默认勾选
│ ☑ [标准] 验收必须含：泛化测试           │

```

签约 = `confirmConstraints(ids)` 批量填 confirmedAt；退役 = `active=false`（不删，可溯）。

## 15. 边角情况表

| 情况 | 处理 |
|---|---|
| 双击 👎 | runId 粒度幂等，第二次忽略 |
| 👎 原因是废话 | §4 质量门槛：只记事件不生成提案 |
| 新旧条款冲突 | 签约时编辑距离粗检 → 并排展示二选一 → supersededBy 落败方 |
| 场景删除 | 账本随场景走（跨场景偏好层本版不做，scope 字段留钩子） |
| pendingConfirm 堆积 >20 | 30 天未确认自动过期清除 |
| 重放中途崩溃 | 走现有失败路径，记 rejected |
| 老场景无 ledger | tier 从折算值起判，通常 spot/full——保守正确 |

## 16. 灰度策略（routingMode 三档）

- **legacy**（默认，上线初期）：账本只记不用——采集/签约面全开，路由/闸门动态化不生效。零行为变化，纯攒数据。
- **spot**：闸门动态化 + 自检启用，路由仍走旧路。
- **full**：双路路由 + 体检 + 统一降级。

dogfood 两周、曲线确实下降后推默认。每档改回即回滚，账本数据无损。
