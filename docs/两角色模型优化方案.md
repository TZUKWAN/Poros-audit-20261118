# SceneFlow 两角色改造方案（Seller · Builder · 分寸资产）

> 版本：v1.0（2026-11-15）
> 前置：分寸账本 v1.0 已发布（`docs/分寸账本发布说明.md`，627 测试绿）
> 理论基础：百度世界 2026「智能组织」三原则 → 本产品的两角色模型落地
> 原则一句话：**seller 和 builder 是仅有的两个结构性角色，agent 织物 + 分寸资产是连接件；每个功能必须给三者之一供能，否则砍掉。**

---

## 0. 设计铁律（三供能检验）

任何新功能/改版，先回答一个问题：

> **这个功能是在给 Seller 供能、给 Builder 供能、还是在给连接件沉淀资产？**

- **S（Seller 供能）**：降低信任成本——看结果、做判断、拿证据。Seller 的输出面对系统外的人类（客户/上级/监管）。
- **B（Builder 供能）**：降低能力生产成本——造场景、签条款、管生命周期。Builder 的输出喂养 agent 织物。
- **A（资产沉淀）**：让连接件复利——条款累积、归因、反事实、跨场景流动。
- 三者都不沾 = **中间层遗物**，进入砍掉/降级评审。

附带两条沿用铁律：只结晶不发明（条款必须带人的出处）；计划是缓存（不投资 DAG 编辑器）。

## 1. 目标架构

```
 Seller（轻）                          Builder（重）
 ┌──────────────────┐                ┌──────────────────┐
 │ 经营头条：本周运行×N│                │ 场景库·五闸门构建   │
 │ 介入×M（↓ vs 上周） │                │ 闸5 签约面         │
 │ 交付收件箱·👍/👎    │                │ 条款生命周期面板    │
 │ 信任报告（导出）     │                │ 自检链配置          │
 └────────┬─────────┘                └────────┬─────────┘
          │ 批准/打回/反馈（判断信号）            │ 分寸信号
          ▼                                   ▼
 ┌──────────────────── 连接件 ────────────────────┐
 │  Agent 织物：编排·执行·路由·自检（已有，基本不动）  │
 │  分寸资产：账本 = 场景层 ∪ 团队层（本次升级核心）    │
 │            归因（helped/hurt）+ 反事实（holdout） │
 └────────────────────────────────────────────────┘
```

分形事实：五闸门已经是这个模型的单人雏形——人只在判断点出现。本方案做的是把这个分形补完整：**给 Seller 端补轻界面，给 Builder 端补生命周期管理，给资产层补科学性和组织流动性。**

## 3. 数据模型演进（PR-1：账本科学）

### 3.1 新增字段（全部向后兼容，zod default 补齐）

```ts
// ledger.ts
ConstraintOrigin += { actor?: string }        // 提案/签约人（多用户预备，单人版=本机用户名）

Constraint += { layer: "scenario" | "team" }   // 默认 "scenario"；team 层见 PR-3

ScenarioLedger += {
  attribution: Record<constraintId, {
    helped: number;      // 注入且回合干净收尾
    hurt: number;        // 注入且被打回/纠正
    heldoutRuns: number; // 该条款处于对照组、未注入的运行数
  }>;
}

// 每次运行结算时（recordRunOutcome 入参扩展）
RunOutcomeParams += {
  injectedConstraints: string[];  // 本轮实际注入的 active 条款 id
  holdout: boolean;               // 本轮是否为对照组（见 §3.3）
}
```

### 3.2 归因规则（结算事务内完成，纯函数）

```
outcome == accepted（干净收尾）  → 本轮注入的每条 helped++
outcome == rejected | corrected  → 本轮注入的每条 hurt++
holdout 轮                       → 不归因，heldoutRuns++（进基线）
suspected                        → 不归因（两边不可信，沿用现有语义）
```

### 3.3 反事实对照组（advisory 专属）

- **确定性哈希**：`hash(runId) % 100 < 15` —— 同一 run 永远同一结果，基线可复现。
- **安全边界**：`must_contain` / `must_not_contain`（机械/标准类）**永不进对照组**——安全条款无条件执行。仅 advisory（偏好类）可被抽走。
- **净增益指标**（信任报告的核心数字）：
  `条款净增益 = 注入轮成功率 − 同期 holdout 轮成功率`
  这是「条款到底有没有用」的反事实证据，回应 MeowCode 已验证的机制。

### 3.4 生命周期自动化（决策点，默认开启）

| 状态迁移 | 条件 | 动作 |
|---|---|---|
| pendingConfirm → active | advisory 且 helped≥2 且 hurt==0 | 自动转正 + chat 通知「已转正，可在账本面板退役」+ journal 留痕（actor=evaluator） |
| active → retired | hurt≥2 | 自动退役（文件保留可溯，hits/helped/hurt 冻结显示） |
| retired → tentative | 人工在面板重新激活 | 手动路径保留 |

阈值取 2 而非 MeowCode 的 3：本产品的 run 是整场景执行，单次信号重于单回合。闸5 人工签约仍是主路径，自动转正只回填「用户忘了签但反复被验证」的条款。**若 dogfood 显示误转正，改回「建议转正 badge + 手动确认」——预留开关 `autoPromote: boolean`（settings）。**

### 3.5 防退化守卫（进 proposeConstraint）

同类条款更新时：新子句 < 旧子句 60% 且**丢失关键 token**（命令 flag、日期格式、字段名——沿用 outputdiff 的 added-稳定子串提取器）→ 拒绝并入，保留旧条款，记 journal(reject, reason=lossy)。防「`pnpm publish --tag latest` 被精炼成 `pnpm publish`」。

### 3.6 测试矩阵（PR-1 DoD）

```
归因：干净收尾→helped++ / 打回→hurt++ / holdout 轮不归因 / suspected 不归因
对照：hash 确定性 / must_* 永不 holdout / 净增益计算（注入 4 成功 3 vs holdout 2 成功 0 → +0.35）
生命周期：helped=2,hurt=0→自动转正+通知 / hurt=2→退役冻结 / 重新激活路径 / autoPromote=false 时只出 badge
守卫：丢 flag 拒绝 / 正常扩写放行 / 旧条款保留
兼容：老记录无 attribution/actor/layer → zod default 补齐，549+ 全绿
```

## 4. 团队层账本（PR-2：资产的组织流动性）

### 4.1 形态：文件即组织（不建服务端）

```
~/.pi/scenario/team-ledger.json     ← 团队层（git 同步，v0 唯一共享机制）
~/.pi/scenario/scenarios.json       ← 场景层（现状，含各自 ledger）
```

- team-ledger 只装 **constraints**（偏好/标准），不装 runStats——统计天然属于场景，资产天然属于组织。
- 格式对 git 友好：数组追加式、id 稳定、一行一字段；文档化「团队同步 = 提交这个文件」。冲突策略：load 时按 clauseKey 去重，**两边都留、场景层胜出**，冲突可见于面板。

### 4.2 解析顺序（注入/自检收条款时统一走 `activeConstraintsAll`）

```
active(scenario) ∪ active(team)  ——clauseKey 冲突时 scenario 覆盖 team
```

改点：`selfcheck` 收集处、模板A 组装处、闸5 已生效清单（团队条款带 `[团队]` 徽章）。

### 4.3 签约面升级

闸5 清单每条新增勾选「同时存入团队层」（默认仅场景层）；存入团队层时 origin.actor 记当前用户名（settings 新增 `userName`，默认取 OS 用户）。

### 4.4 测试矩阵

```
解析：scenario 覆盖 team 同义条款 / 两层并存注入 / clauseKey 去重
写入：勾选存入团队层→team-ledger.json 落盘 actor 记录 / 不勾选仅场景层
迁移：无 team 文件首次启动创建空壳（幂等）
```

## 5. Builder 端：条款生命周期面板（PR-3 前半）

场景详情账本面板升级为三栏生命周期视图：

```
┌ 条款生命周期 ────────────────────────────────┐
│ [待签约 2]  [生效 5]  [已退役 1]              │
│ ── 待签约 ──                                  │
│ ☑ 行动项带负责人  命中2 帮2害0  [转正][忽略]    │
│ ── 生效 ──                                    │
│ 日期用YYYY-MM-DD 命中5 帮6害1 净+0.4 [退役]   │
│ ── 已退役 ──                                  │
│ 要简短(团队) 帮0害2  [重新激活]                │
└──────────────────────────────────────────────┘
```

- 每条显示：hits、helped/hurt、**净增益**（有 holdout 数据时）、`[团队]` 徽章、来源原话（hover）。
- 操作：转正/退役/重新激活/忽略——退役沿用 retireConstraint（不删可溯），全部走 journal。

## 6. Seller 端：经营头条 + 信任报告（PR-3 后半）

### 6.1 经营头条（面板顶栏常驻，一行）

```
本周运行 ×12 · 人工介入 ×7（上周 ×11 ↓36%）· 条款 5 生效 · 净增益 +0.4   [信任报告]
```

数据源：interventions 按周聚合（已有数据，纯前端计算）。这就是 **inverse-DAA**：DAA 度量采纳，介入曲线度量成熟。

### 6.2 信任报告（可导出的销售证据）

- 范围：单场景 / 全工作区（周报）。
- 产物：markdown 写入 `~/.pi/scenario/reports/`，面板一键生成并复制路径。
- 内容结构：
  1. 头部数字：运行数、介入数与环比、tier 现状、条款数
  2. 介入曲线（字符 sparkline + 数据表：每次 run 的 total）
  3. 条款贡献表：helped/hurt/hits/净增益，按净增益降序
  4. 反事实段：「15% 对照组期间，无条款运行成功率 X%，有条款 Y%」
  5. 诚实脚注：suspected 不计、无人值守规则、灰度档位
- 这是 seller 拿去对客户/上级说话的东西：「我们的 agent 上月要人盯 11 次，本月 7 次，证据在这。」

## 7. Dogfood 案例包（PR-4：第一个真实曲线故事）

商业楔子 = FDE 型 seller-builder 杂交体（先部署进客户/团队场景、边交付边结晶分寸的人）。两角色模型预言这类人会大量出现。

- 选定垂类：**ares 竞赛备赛链**（领域库已就绪）或 metis 研究流水线，二选一。
- 协议（写进 `docs/dogfood-协议.md`）：
  1. 一名真实用户 + 一条真实重复性工作，跑 2 周
  2. 每周出一份信任报告（自动产物）
  3. 验收问题只有一个：**介入曲线第二周是否低于第一周？**
- 产出物：一份带真实曲线的案例 markdown（对内讲故事 / 对外做内容）。

| # | 风险 | 缓解 |

## 10. 不做清单（scope 铁律）

- ❌ 多用户服务端/账号体系（v0 = git 同步文件；出现真实多人冲突痛点再议）
- ❌ DAG/计划编辑器（计划是缓存）
- ❌ 无人类出处的自动约束（只结晶不发明）
- ❌ 模型自评置信度（外生统计铁律不变）
- ❌ Seller 端做重（不做成 BI 面板——一行头条 + 一份报告，克制）
- ❌ 追赶 MeowCode 的提示词学习路线（差异化=可执行判据+行为分级，不跟进软建议路线）

## 11. 验收剧本（全部完成的 DoD，10 分钟可演示）

```
1. 构建场景 → 闸3 打回「行动项带负责人」→ 闸5 勾选「存入团队层」签约
2. 换一个同域场景运行 → 团队层条款被注入（chat 可见 [团队] 徽章）→ 自检拦截缺负责人产出
3. 同需求连跑 3 次干净收尾 → 账本面板该条款 helped=3；再打回一次 → hurt=1
4. 顶栏头条显示「本周运行×N 介入×M ↓」；点击生成信任报告 → 打开 reports/*.md
   含曲线/条款贡献表/净增益（或「样本不足」脚注）
5. 一条 advisory 处于 holdout 轮 → 报告对照组段可见基线数字
6. 故意提一条丢失 flag 的退化条款 → 被守卫拒绝，旧条款保留
7. dogfood 协议文档就位，垂类已选定，埋点核查通过
```

---

**与既有资产的关系**：本方案不推翻 v1.0——分寸账本四铁律、置信度引擎、自检链、反应窗全部保留；做的是把单人账本升级为**有反事实证据的组织资产**，并把产品的两端（Seller 轻界面 / Builder 重工具）补成形。北极星不变：**第 N 次人工介入次数，单调下降。**
