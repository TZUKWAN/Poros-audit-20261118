**Poros PC 交互研究与流程推演**

本文件保留研究阶段的官方资料与推演。获批准后的实现契约和实际验证另见 [交互实施与验证](PC_INTERACTION_IMPLEMENTATION.md)，研究情境不作为运行证据。

研究日期为 2026 年 11 月 24 日，供刘总评审。本文是研究交付。文中的 Poros 新流程均为设计推演，实施状态为待评审。上轮本地界面简化尚未得到产品认可。

**1. 先明确研究结论适用的范围**

本轮逐页读取扣子、Dify、FastGPT、Microsoft Copilot、Claude、Manus、ChatGPT Workspace Agents 和 n8n 的官方材料，核对公开产品截图，并只读检查 Poros 当前源码。截图来自厂商文档，已经逐张查看。竞品账号内流程、套餐差异和实际可用性尚未亲自走查。文档列出的操作是官方描述的行为。后文的 Poros 取舍是本人的分析，用户理解程度还需要走查验证。

本次研究关注的最小单元包括入口、用户当前知道什么、用户作出什么决定、系统给出什么反馈、下一步去哪里、离开后如何回来、失败后如何继续。一个按钮是否存在，只能说明入口是否具备，完整交互还涉及它前后的状态与权限。

| 产品 | 本轮核查重点 | 版本与证据注意事项 |
| --- | --- | --- |
| 扣子 | 自然语言创建、开发与预览、调试、发布与历史 | 当前扣子编程与旧低代码平台分别记录。官方说明旧低代码平台已停止向新注册用户开放 |
| Dify | Chatflow 与 Workflow 的使用界面、人工输入、日志、版本和反馈 | 人工输入节点有新旧版本，接收者验证方式随版本变化 |
| FastGPT | 成员使用门户、执行详情可见性、来源引用、草稿与发布、排障 | 商业版首页和部分数据面板存在版本条件 |
| Microsoft Copilot | Describe、Configure、Try it、发布到组织、按来源权限使用 | Agent Builder 与 Copilot Studio 承担的扩展能力存在差异 |
| Claude | 持续会话、执行中引导、项目上下文、产物修改 | 统一聊天与 Cowork 的体验正在分批推出，用户可能仍处于旧界面 |
| Manus | 项目、按任务连接服务、等待用户、后续消息、任务共享 | 公开示意图标注 Manus 1.6。当前文档/API 另行核对，API 能力不推断为同名 UI 按钮 |
| ChatGPT Workspace Agents | 助手发现、构建预览、连接身份、分享权限与编辑冲突 | 研究重点为业务使用和治理机制 |
| n8n | 在具体工具操作前暂停、展示参数、审批后继续 | 用于补充人工介入机制，工作流编辑器面向构建者 |

**2. 扣子的创建、调试和使用分别承载什么意图**

扣子当前的编程文档把创建智能体作为一个开发任务。用户输入的是“帮我开发一个……助手”，产出的是可测试和部署的智能体。它的开发对话和右侧对话预览有各自明确的对象。[扣子开发智能体](https://docs.coze.cn/guides_vibe_coding_agent)

| 顺序 | 开发者操作 | 系统反馈与落点 | 交互含义 |
| --- | --- | --- | --- |
| 1 | 在编程首页选智能体，描述要开发的能力 | 创建项目，展示开发进度 | 用户知道这次请求会形成一个可复用的助手 |
| 2 | 按需要附材料、加技能、选编程模型 | 这些条件服务于开发过程 | 创建助手时所用模型与未来助手运行模型要有明确归属 |
| 3 | 在左侧继续描述调整要求 | 更新项目，右侧可预览 | “改助手”有独立上下文 |
| 4 | 在右侧向生成的助手提问 | 查看助手如何回答和使用能力 | “试用助手”与“要求开发工具改助手”各自有入口 |
| 5 | 查看版本历史并选定版本回滚 | 当前编程文档说明会产生新的部署版本，保留历史 | 历史版本、当前开发内容和部署内容分别可辨 |

旧低代码文档描述的顺序是选择工作空间、创建智能体、填写名称用途，再进入人设、技能、预览调试的编排页，最后选择渠道并填写发布记录。这个旧流程可以研究信息关系，其开放范围应按当前说明理解。[低代码快速开始](https://docs.coze.cn/guides_agent_quick_start)

调试还有明确的进一步入口。在一条预览回复下打开调试按钮，查看对应请求的调用树、节点输入输出与耗时。用户在会话中先看到回复，构建者能从这条回复进入技术证据。[扣子预览与调试](https://docs.coze.cn/guides_preview_debug)

对 Poros 的推论是，创建助手时的对话应该明确围绕“助手以后如何工作”。试用区域应该显示“正在测试草稿”。日常成员打开已发布助手时应该进入它的使用会话。三个地方即便都使用输入框，也需要通过标题、对象和结果来建立边界。

**3. Dify 对持续对话与一次性流程分别给了哪些反馈**

| 体验 | 用户如何开始 | 请求之后看到什么 | 如何继续 | 官方依据 |
| --- | --- | --- | --- | --- |
| Chatflow Web App | 打开应用，有必要变量时先完成前置表单 | 同一会话中的问答和来源 | 继续提问、切换历史会话、新建会话 | [Chat Web Apps](https://docs.dify.ai/en/self-host/use-dify/publish/webapp/chatflow-webapp) |
| Workflow Web App | 填写开始节点定义的业务输入，点击 Execute | 本次执行的处理反馈和输出 | 保存、复制结果，或生成另一个结果 | [Workflow Web Apps](https://docs.dify.ai/en/self-host/use-dify/publish/webapp/workflow-webapp) |
| 发布后遇到问题 | 构建者到日志搜索实际会话或运行 | 原输入、回复、反馈及追踪 | 用 Test With Params 带原参数回编辑器复现 | [Logs](https://docs.dify.ai/en/self-host/use-dify/monitor/logs) |
| 要发布修正 | 在草稿修改和测试，再 Publish Update | 新版成为线上版本，继续保有草稿 | 从历史恢复到草稿后再次发布 | [Version Control](https://docs.dify.ai/en/self-host/use-dify/build/version-control) |

官方截图中，Chatflow 左侧有 New chat 和会话历史，反馈按钮属于具体回复。Workflow 图中，左侧业务输入和 Execute 与右侧输出相对应，还有 Run Once、Run Batch、Saved。控件的意义由应用承诺的工作过程决定。

Dify 的新版 Human Input 节点允许把表单交给发起人或指定人员。表单展示当前需要判断的内容，按钮决定后续分支。首位有效答复关闭请求，超时有独立路径。其示例还把草稿与反馈带入下一轮修改。这里每次等待都有明确的接收者和待处理内容。[Human Input](https://docs.dify.ai/en/self-host/use-dify/nodes/human-input)

反馈还有另一条路径。Dify 可以把调试或日志里的答案修改后保存为标注，后续按语义匹配返回维护好的答案。这种复用机制与 Poros 的 Judgment 检查有不同的执行含义。Poros 采用何种规则，要在产品说明里交代其影响。[Annotation System](https://docs.dify.ai/en/self-host/use-dify/monitor/annotation-reply)

对 Poros 的推论是，必须先定义用户是否能在同一项工作里持续交流、修改成品和恢复进度。如果承诺这些能力，就需要有连续会话及产物修订的真实契约。现有的执行记录可以继续提供证据，用户能理解的工作对象需要覆盖多轮交流。

**4. FastGPT 怎样让成员使用应用、让构建者处理问题**

| 顺序 | 入口和操作 | 反馈与后续 | 需要学习的关系 |
| --- | --- | --- | --- |
| 1 | 登录成员从 Portal 打开应用 | 左侧组织应用、收藏和最近使用，保有会话历史 | 发现应用和使用应用连在一起 |
| 2 | 使用应用提问 | 回复按配置展示执行状态、引用片段 | 用户能先核对业务结果 |
| 3 | 根据权限查看来源或详情 | 引用片段、全文、原始文件下载分别控制 | 看到答案、看到引用和下载原文件涉及不同范围 |

以上来自成员门户文档。门户的显示设置和已发布应用的运行逻辑各自有作用范围，调整展示可见性要按目标成员权限核查。[FastGPT Portal](https://doc.fastgpt.io/guide/build/publish/portal)

构建者保存草稿后可以调试当前编辑内容。外部入口使用已发布版本。查看旧版本会把它带入编辑器，再次保存并发布才影响线上。发布之后还要经实际使用入口验证。[发布版本与渠道](https://doc.fastgpt.io/guide/build/publish/versions)

当成员反馈问题，构建者在会话日志定位输入和回复，再沿节点查看知识召回、工具请求、模型输出和错误。修正后重新发布并从实际入口检查。反馈由具体回复追溯到配置原因。[会话日志与执行详情](https://doc.fastgpt.io/guide/build/logs)

免登录分享链接还有独立的使用身份与历史限制，不能据此推定企业登录门户具备同样的跨设备行为。对 Poros 而言，日常工作应继续以已认证成员身份和服务端持久记录恢复。[分享链接说明](https://doc.fastgpt.io/guide/build/publish/link)

**5. Microsoft 如何引导构建、试用、分发和按材料使用**

| 顺序 | 用户动作 | 系统响应 | 后续决定 |
| --- | --- | --- | --- |
| 1 | New agent 后描述用途，或使用模板 | 逐步形成名称、说明、指令、知识来源和建议请求 | 描述会转成可查看的配置 |
| 2 | 到 Configure 查看配置 | 能核对知识范围、能力和建议请求 | 继续修改已明确的配置 |
| 3 | 在 Try it 试用 | 与助手对话检验表现 | 根据试用结果继续完善 |

这个流程说明自然语言创建与结构化配置可以相互衔接。官方配置截图也把知识来源、能力与建议请求放在同一个助手的配置上下文里。[Agent Builder](https://learn.microsoft.com/en-us/plugins/agent-builder-build-agents)

分发对象继续影响后续步骤。面向指定人员或组的分享与提交到组织目录各有流程。组织目录提交后由管理员审查，使用者随后在组织可用的入口发现助手。[组织分发](https://learn.microsoft.com/en-us/copilot/manage/copilot-agent-store)

在 SharePoint 文档库，用户能选中文件后直接提问，也能在对话框中加文件。这里当前材料会成为发起请求的起点。文件和助手的访问权限分别生效。[使用文件提问](https://support.microsoft.com/en-au/sharepoint/copilot-in-sharepoint/interact-with-agents-in-sharepoint) [页面、助手与来源的权限](https://support.microsoft.com/en-us/sharepoint/pages-in-sharepoint/use-agent-chat-web-part)

Copilot Studio 的测试面板提供从回复定位到节点的路径，并可管理测试连接。官方明确说明设计时测试无法完全复制已发布渠道的行为。对 Poros 的草稿测试同样需要标明使用版本、测试身份、实际连接和执行范围。[Copilot Studio 测试](https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-test-bot)

**6. Claude 如何把说需求、执行和修改交给同一会话**

当前新版官方说明，用户在同一会话提出快速问题或多步骤工作，由系统选择处理方式。Auto、Manual 控制何时介入，工作中可以停止或引导方向。该体验分批推出，因此账户截图和新版说明可能处在不同阶段。[统一聊天与 Cowork](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude)

| 顺序 | 用户操作 | 可观察反馈 | 后续回到哪里 |
| --- | --- | --- | --- |
| 1 | 描述要得到的结果，附需要的上下文 | 系统展示处理过程 | 当前会话 |
| 2 | 执行中补方向或离开 | 可跟进进度，后续回来查看 | 同一个持续保存的会话 |
| 3 | 打开生成的产物 | 产物在会话旁出现 | 会话与产物保持联系 |
| 4 | 对产物提出修改，或在文档选中文字后要求修改 | 修改作用于选定内容 | 继续编辑、分享或导出 |

任务过程来自 Cowork 使用指南，产物编辑来自 Artifacts 文档。这里的“继续做”和“继续修改”都能从原工作找到对象。[Cowork 入门](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork) [Artifacts 编辑与导出](https://support.claude.com/en/articles/17153992-what-are-artifacts-and-how-do-i-use-them)

项目则承载可重复使用的资料和指令。项目上下文对新工作提供背景，项目共享和个人会话内容还需要各自的权限说明。[Cowork 项目](https://support.claude.com/en/articles/14116274-organize-your-tasks-with-projects-in-claude-cowork)

对 Poros 的推论是，用户可以在普通输入框说“把刚才那份改成两页”，同时界面明确显示目标产物和本次修改范围。保持会话连续性与限制运行权限需要同时成立。

**7. Manus 怎样在当前任务里补齐连接和保持上下文**

| 顺序 | 用户遇到的情况 | 产品处理 | 用户仍需决定什么 |
| --- | --- | --- | --- |
| 1 | 请求涉及未启用的服务 | 在当前会话推荐相关连接器 | 启用还是跳过 |
| 2 | 服务账号尚未连接 | 卡片显示 Not connected 和 Connect | 完成账号授权 |
| 3 | 审阅所需连接后点击 Apply | 任务继续处理 | 所用账号及权限需要可理解 |

上述按钮与状态已在官方配图核对。来源页面说明推荐、授权和继续执行连在当前对话中。截图标注 Manus 1.6，足以研究此交互顺序，无法据此认定所有账户当前界面完全一致。[任务内推荐连接器](https://www.manus.im/blog/manus-recommended-connectors)

项目可以保存指令、资料、技能和推荐连接器，用户在其中开始新任务。队友的账号连接、项目共享资料和个人任务可见性各自有含义。[项目功能说明](https://www.manus.im/features/projects) [项目连接器流程](https://www.manus.im/blog/projects-connectors)

当前 API 文档另外明确后续消息可以继续同一个 task，连接器选择有沿用与替换规则。他人的任务还涉及写权限、忙碌和所有者决定。这个证据只用于确认持续交互与权限需要真实的服务端状态。[task.sendMessage](https://open.manus.im/docs/v2/task.sendMessage) [连接器选择](https://open.manus.im/docs/v2/connectors)

对 Poros 的推论是，用户在一次工作里发现缺 Kdocs 账号时，可以原地完成配置再返回原请求。个人凭证、助手已审批能力和项目授权都要保留各自的判断，连接成功后还应展示这次可读取的范围。

**8. ChatGPT Workspace Agents 与 n8n 补充的治理细节**

ChatGPT 的助手列表分别承载最近用过、自己创建和团队目录。创建流程可先描述用途、审阅草案、进入构建并预览。使用、编辑和拥有者权限存在区别，连接也有运行者自己的账号和助手拥有的共享账号两种语义。Poros 当前采用发起人连接，可以在使用页把这个事实说清楚。[Workspace Agents 官方帮助](https://help.openai.com/en/articles/20001143-chatgpt-workspace-agents-for-enterprise-and-business)

n8n 的人工审批放在需要审核的工具调用前。请求展示要执行的工具及参数，批准才执行，拒绝则把决定反馈给执行流程。审批可以通过与主会话不同的渠道送达审阅者。[n8n 工具审批](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools)

Microsoft 的 RFI 也明确“暂停、指定接收者提供信息、把回答传到后续步骤”。Dify 还明确无法送达、超时和首人答复等分支。Poros 需要把发起人确认、独立审阅和业务补充材料分别建模，再在会话中向用户呈现当下需要的事情。[Microsoft RFI](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/flows-request-for-information) [Dify Human Input](https://docs.dify.ai/en/self-host/use-dify/nodes/human-input)

**9. 对照 Poros，哪些地方让用户的工作接不上**

下表记录实施前本地原型的观察。代码链接指向对应模块；新版本已按实施文档调整，不能把这些旧观察理解为新版本现状。

下表来自当前源码只读核查。这里判断的是交互与契约的衔接，未以新的运行测试断言功能故障。

| 当前表现 | 用户需要自己推断的事情 | 对交互的影响 | 源码证据 |
| --- | --- | --- | --- |
| 登录要求组织 ID | 自己属于哪个内部标识 | 缺少组织背景的新成员难以开始 | [登录](../web/src/App.tsx) |
| 首页默认取第一个可用的非项目限定 Agent | 为什么是它、适合什么工作 | 数据顺序决定处理者 | [默认选择](../web/src/views/workspace.tsx) |
| 从项目点任务会切到全局运行中心 | 自己是否还在原项目、如何返回 | 工作上下文由用户记忆维持 | [切换入口](../web/src/App.tsx) |
| 文件行主要提供预览、下载与使用记录 | 上传后怎样交给助手 | 材料和发起工作存在往返选择 | [文件操作](../web/src/views/projects.tsx) |
| “纠正结果”表单含规则类型和作用域 | 眼前修改是否会影响以后 | 本次修改需求被导向长期规则管理 | [纠正表单](../web/src/views/correction.tsx) |
| 任务由 prompt、输入文件与冻结快照创建 | 后续补充如何关联先前输出 | 需要持续会话契约支持多轮工作 | [Task](../prisma/schema.prisma) |
| Run 是某次尝试的状态、输出和证据 | “重试”和“修改结果”有什么区别 | 当前重试不能承担所有继续操作 | [Run](../prisma/schema.prisma) |
| 敏感能力根据已授予工具列表确定，任务先进入 BLOCKED | 本次为什么需要审批、准备做什么 | 有工具权限就会产生整项工作的等待 | [任务门控](../src/server/routes/index.ts) |
| 采纳入口受 SUCCEEDED 限制 | 未验证结果能否表达个人意见 | 人的反馈与自动质量状态需要分别表达 | [采纳条件](../src/server/routes/index.ts) |
| 设置内保存连接后另点测试 | 测试通过后哪位助手能用它 | 账号可用与助手授权缺少就地解释 | [连接操作](../web/src/views/integrations.tsx) |
| 上一轮把审批放进“管理” | 审阅者每天要去哪里处理待办 | 高频审批的发现路径变长 | [管理导航](../web/src/App.tsx) |

上一轮将“从项目和材料开始”过早固定为主方案。项目对持续协作有价值，临时提问、单次处理附件和首次体验也应该有清晰入口。现在需要先定义所有入口进入同一项工作后如何保持对象、权限和上下文，再决定首页布局。

**10. 建议采用的对象关系，以及用户如何感知它们**

以下均为待评审的设计判断。Poros 的企业助手构建、隔离执行、独立审批和版本治理继续作为约束。

| 对象 | 用户理解的含义 | 应承载的内容 | 用户何时需要看到 |
| --- | --- | --- | --- |
| 组织 | 我正在哪个团队工作 | 身份、组织策略、成员与资源授权 | 登录后顶层背景，切换时明确 |
| 项目 | 这项工作属于哪个业务背景 | 成员、共享材料、项目规则与工作索引 | 从项目进入时自动带入，临时工作可用个人范围 |
| 助手 | 谁按什么方式帮助我 | 用途、已批准配置、工具、来源和版本 | 开始时说明处理者，切换时说明影响 |
| 会话 | 围绕同一个目标持续协作的记录 | 用户请求、补充、系统答复、待处理问题和产物 | 日常工作主界面 |
| 执行 | 助手为其中一个请求开展的一次处理 | 输入快照、权限、实际模型、事件、尝试与错误 | 进度、等待、排障与成本核对 |
| 产物 | 我可以查看、修改、交付的东西 | 正文或文件、版本、来源、对应请求 | 结果区域与项目产出 |
| 规则 | 以后哪些工作要遵循什么要求 | 适用范围、修订、审批、来源与检查证据 | 明确发起复用或审核时 |

关系可以这样读。一个项目组织多项工作，每项工作有连续会话。一条用户请求可以需要一次或多次执行尝试，后续要求修改会形成新的请求与产物版本。每次执行保留自己的冻结快照和实际证据。用户在界面上始终能知道“这是哪项工作、这次正在处理哪条要求、当前是哪版结果”。

固定助手负责明确领域时，直接打开它最容易理解。泛化入口能成立的前提，是组织已经提供真实可用、获授权的通用助手及明确的处理边界。所有入口都应显示当前处理者，助手选择只在有决定价值时出现。

**11. 首屏的三种可能路径如何判断**

| 入口 | 适用情况 | 必须满足的条件 | 使用阻力 | 本轮建议 |
| --- | --- | --- | --- | --- |
| 从“新工作”输入需求 | 临时分析、写作、处理附件 | 已明确配置可用默认助手，或当场给出用途清楚的选择 | 默认助手缺失时要解释下一步 | 作为可用主入口，依真实配置呈现就绪状态 |
| 从助手目录打开业务助手 | 用户明确知道要“合同审阅”“周报整理”等 | 有用途说明、输入要求和可见范围 | 目录过多时需要搜索与最近使用 | 与新工作并行，打开后进入同一种会话界面 |
| 从项目或文件发起 | 已有业务背景和材料 | 当前项目、选定文件与助手的授权一致 | 每次强制建项目会增加负担 | 从已有上下文直接带入，个人工作保留入口 |

因此，新成员可以先看到真实可用的助手及各自能做什么，老成员可以继续最近工作。构建者能从助手进入“编辑”，审阅者能直接看到自己的待办。组织管理通过账号或组织入口到达。这些入口的具体排布还要结合流程原型评审。

开始一项工作前，用户有四类值得确认的信息。第一是准备完成的结果，第二是这次可用的资料，第三是负责处理的助手，第四是工作可见范围。模型版本、运行 ID 和工具注册名放在可查看的详情里，只有影响执行条件或需要授权时才提升显示层级。

**12. 详细交互流程**

后续逐项规定动作前提、用户操作、系统反馈、状态变化和异常恢复。所有界面文案均为供评审的示例，未作为实际运行结果。

**12.1 首次进入与就绪检查**

| 步骤 | 用户操作 | 系统必须显示或完成 | 失败与下一步 |
| --- | --- | --- | --- |
| 1 | 打开部署地址或受邀入口 | 显示组织名称与登录方式。组织由部署或邀请背景确定 | 多组织账号先选择组织名称。当前后端仍需组织 ID，体验变更需新增可靠的组织发现方式 |
| 2 | 登录 | 返回用户有权使用的助手、项目和待办 | 无权使用时说明缺少的资格与可联系对象，避免空白页 |
| 3 | 首次浏览 | 看到助手的用途、所需材料与可得到的产物 | 有助手但模型不可用时，列出具体原因和配置入口 |
| 4 | 存在个人模型前置条件 | 在可保留返回位置的面板填写端点、模型和密钥 | 保存成功后继续真实生成测试，目录查询与生成验证分别显示 |
| 5 | 生成验证通过 | 显示验证账号、模型和时间，回到原助手或工作 | 403、账户验证要求、超时保留准确原因。修正连接后回原位置 |
| 6 | 开始工作 | 在真实可用助手上出现明确的使用入口 | 组织尚无已发布助手时，构建者可创建，普通成员可申请开放已有能力 |

就绪信息应直接回答“我还差哪一步才能用”。管理员负责部署连接时，普通成员的操作指向管理员。采用个人连接时，当前成员可以处理自己的配置。两种归属必须随实际部署策略显示。

模拟预览需要单独的环境说明。打开预览能验证操作和记录，不足以说明真实模型已能完成业务。当前 Poros 的真实模型状态仍应以实际生成探测结果为准。

**12.2 从助手开始一项工作**

| 步骤 | 用户看到什么 | 用户操作 | 系统行为与下一状态 |
| --- | --- | --- | --- |
| 1 | 助手名称、用途、可以处理的资料、示例请求 | 点“使用” | 打开新会话，固定当前助手和已批准版本 |
| 2 | 输入框、添加资料、个人或项目范围 | 输入目标，可点示例预填 | 示例只填入草稿，等待用户发送 |
| 3 | 选定资料的名称与处理状态 | 添加、移除或替换附件 | 上传与读取准备独立显示，处理中材料仍在原位置 |
| 4 | 本次资料范围与可见性 | 点“开始”或发送 | 服务端验证助手、项目、文件、模型及连接条件 |
| 5 | 请求已保存的回执 | 等待，或按需要补充 | 请求进入会话和历史列表，有稳定地址可再次打开 |
| 6 | 助手的处理进度 | 查看概要或展开步骤 | 任务在服务端执行，事件进入这条请求的过程记录 |
| 7 | 结果与产物 | 查看、下载、提出修改 | 后续操作继续关联此会话与产物 |

输入足以开工时，直接开始允许范围内的工作。只有影响结果或权限的缺项才需要提问。例如同一项目出现两份同名销售表时，展示名称、日期和来源供选择。用户已经选定文件和时间范围，就沿用该选择。

预检查失败时，保留正文与资料。用户修复条件后再次发送，应明确是否沿用原请求。提交超时但服务端可能已受理时，先查请求回执，避免一次点击形成多次工作。

**12.3 从项目或文件开始，以及跨入口返回**

| 起点 | 点击动作 | 应带入的上下文 | 用户发送前能核对什么 |
| --- | --- | --- | --- |
| 项目概览 | “开始工作” | 项目身份、项目可用助手、已批准的项目指令 | 当前项目及成员可见范围 |
| 项目文件列表 | 选中材料后“交给助手处理” | 文件引用和所属项目 | 文件名称、版本或更新时间、可读取状态 |
| 单文件预览 | “基于此文件提问” | 当前文件与项目 | 当前资料已附在输入区 |
| 已有任务或结果 | “继续处理” | 原会话与当前产物 | 这条消息会接着哪项工作 |
| 全局最近工作 | 打开记录 | 同一会话、项目、实际助手和当前位置 | 原项目入口及结果版本 |

不同入口到达的同一项工作应有同一地址。打开来源文件可以使用侧面板，关闭后回到正在读的结果。浏览器后退保留项目列表的筛选和滚动位置。

切换项目是一项会改变范围的动作。已经选择的文件逐一重新校验，受影响的材料用可读说明标出，用户能够取消切换。若历史消息已使用原项目资料，继续工作应保留原归属，改在其他项目处理时明确新建一项带选定材料的工作，并按目标范围重新授权。

**12.4 文件与外部知识的完整使用过程**

| 文件阶段 | 用户反馈 | 可操作项 | 与执行的关系 |
| --- | --- | --- | --- |
| 上传中 | 文件名与实际上传进度 | 取消上传 | 尚未成为可读输入 |
| 已存储 | 已保存，并说明是否支持读取 | 预览、移除 | 存储完成只说明文件已保存 |
| 准备读取 | 正在提取文本，或等待任务时读取 | 保留文件，按可用能力继续 | 显示实现实际采用的时机 |
| 可读取 | 文本预览、节选或范围限制 | 确认附加、查看原文 | 模型使用的内容范围可追溯 |
| 读取失败 | 明确不支持、加密、损坏或没有文本层 | 替换、移除、提供可读版本 | 必需文件未就绪时标明阻塞原因 |
| 已被使用 | 来源标识与具体运行关联 | 查看引用和处理记录 | 显示实际读取结果与是否截断 |

对当前 Poros，文件上限、支持格式和节选范围沿用已有真实能力。扫描 PDF 需要 OCR 时显示缺少这一处理能力。Word、Excel 的来源定位只显示实际能提供的位置，证据能定位到段落或单元格时再提供对应入口。

Kdocs、IMA 和 TinyFish 在工作过程中属于资料或工具来源。用户可选择具体文档、知识范围或网页查询，看到真实命中项和引用。连接器测试与一次任务中的实际调用分别留下结果，用户应能理解“账号可用”“本次查询完成”“这份内容已用于回答”之间的步骤。

**12.5 在当前工作里配置连接**

| 状态 | 用户操作 | 系统反馈 | 对当前工作的处理 |
| --- | --- | --- | --- |
| 请求需要的个人服务未连接 | 点当前会话中的“连接 Kdocs”等入口 | 打开明确标注个人账号的配置面板 | 保留请求、材料和返回位置 |
| 输入凭证或完成授权 | 保存连接 | 字段清空敏感值，显示保存状态 | 原请求仍待处理 |
| 已保存但未验证 | 点真实连接验证 | 显示实际测试及供应商错误 | 未验证状态下说明恢复动作 |
| 验证通过且助手已获相关授权 | 点“返回工作” | 展示可用范围 | 创建下一次执行或在有效检查点继续 |
| 已连接但助手无权限使用 | 查看缺少的能力或审批 | 指向该助手的配置负责人 | 保留当前请求，避免让用户重复配置账号 |
| 工作中连接失效或更换 | 修复个人连接 | 标明旧连接修订已失效 | 根据冻结快照重新校验，新建尝试或请求重新授权 |

当前 Poros 把连接修订冻结在任务中，这能为审计提供依据。修复后的连接是否能用于原任务，需要明确的重新绑定与审批规则。页面显示“继续”时，服务端必须能说明续接的是哪次请求、使用哪个有效修订。

模型选择同样遵循已批准配置。成员可以配置自己的可用连接，助手能否使用某个模型由其授权与已发布策略决定。系统建议的替代项应来自可用的批准范围，并说明对本次工作的影响。

**12.6 长任务、补充要求与中途介入**

| 运行时机 | 主区域显示 | 用户动作 | 服务端需要保证的行为 |
| --- | --- | --- | --- |
| 等待资源 | 已排队，说明可离开 | 离开、取消 | 保有队列状态与稳定工作地址 |
| 读取材料 | 正在读取哪些已选资料 | 查看详情、提出停止 | 记录成功与失败的资料，保留真实来源 |
| 调用工具或模型 | 用业务语言描述当前步骤 | 展开证据 | 展开才出现参数、输出、耗时与错误 |
| 执行中补要求 | 新消息显示已收到及应用时机 | 排入后续处理，或停止后调整 | 已开始的动作使用其原快照，新要求有自己的记录 |
| 缺少决定性信息 | 清楚的问题和必要选项 | 回答、选文件、取消 | 进入真实的等待输入状态 |
| 等待独立审批 | 等待谁审阅、审什么、何时发起 | 查看申请、取消工作 | 审阅决定与后续执行建立持久关联 |
| 界面事件流断开 | 正在恢复进度连接 | 留在页面或稍后返回 | 恢复订阅和读取服务端当前状态 |
| 执行完成 | 当前产物与未解决事项 | 查看、修改、交付 | 终态写入完成后展示相应状态 |

“正在做什么”应来自真实运行事件。无法量化完成比例时，可以显示已完成步骤和当前步骤。用户离开页面不会改变服务端任务状态。

持续会话不要求一开始就具备任意步骤的暂停恢复。最小可行契约可以是在一轮运行中接收下一条要求，标明待本轮结束后处理，停止与恢复也按实际能力展示。要承诺即时转向，就需要可中断动作边界和可靠的恢复点。

**12.7 审批时究竟让人决定什么**

| 审阅对象 | 发生时机 | 要回答的问题 | 审阅后影响范围 |
| --- | --- | --- | --- |
| 助手发布 | 新配置供团队使用前 | 这个版本能用哪些能力、哪些资料、谁可使用 | 后续采用该版本的请求 |
| 当前整项任务 | 现有 Poros 任务门控需要时 | 此请求及所列敏感能力是否获准执行 | 当前任务及冻结范围 |
| 具体动作 | 未来服务端支持动作级门控时 | 此时要对哪个对象做哪项操作，参数和影响是什么 | 被批准的动作及内容范围 |
| 长期规则 | 规则候选生效前 | 规则是否正确、适用于谁、是否冲突 | 后续受此修订约束的工作 |

本轮设计保留现有独立审批要求。由整项任务审批细化到具体动作，需要后端支持，实施前应把当前审批对象如实呈现。发起人同意与独立审阅者决定都有自己的身份和记录。

审批卡片需要包含申请人、工作目标、关联项目、当前助手版本、拟处理对象、拟执行内容、账号身份、影响范围和审批原因。涉及修改时显示内容差异，涉及对外发送时显示接收对象及待发送正文。工具的技术参数在详情展开。

| 审批分支 | 发起人看到什么 | 审阅者能做什么 | 系统处理 |
| --- | --- | --- | --- |
| 待审批 | 已提交，等待具备资格的人处理 | 打开完整证据，批准或拒绝 | 保持等待，禁止发起人自批 |
| 批准 | 获准范围与执行进度 | 查看决定历史 | 仅按冻结内容继续 |
| 拒绝 | 原因及受影响步骤 | 记录可操作的理由 | 当前受控动作终止，允许修改后重新申请 |
| 内容已变化 | 原申请与新要求存在差异 | 查看已失效标识 | 为变更后的内容生成新申请 |
| 重复点击或他人已处理 | 已有决定及处理时间 | 查看现有结果 | 只保留一份有效决定 |
| 资格撤销或申请过期 | 等待原因与恢复路径 | 按当前权限重新分配或处理 | 重新验证资格与动作有效性 |

审阅者的待办应能直接进入这张卡片。发起人在原会话看到审批进度，返回后仍处于同一项工作。没有可用的独立审阅者时，需要在发起前提示并提供组织处理路径。

**12.8 结果、来源、质量与人的判断**

用户打开结果，应先看到这次完成了什么、可使用的产物、仍有的问题和下一步动作。运行编号、调用次数等信息可以从执行详情查看。

| 区域 | 显示内容 | 点击行为 |
| --- | --- | --- |
| 请求与完成情况 | 本条要求、已完成内容、未完成原因 | 回到原始请求，查看过程 |
| 产物 | 文件名或文档标题、版本、生成时间 | 预览、下载、继续修改 |
| 来源 | 实际引用的文件或网页、可定位范围 | 打开对应来源，关闭后回到结果 |
| 检查 | 规则通过、未通过、未检查的具体项 | 查看规则及检查证据 |
| 业务反馈 | 用户对本次结果的评价或修改要求 | 记入这条回复或产物 |
| 正式采纳 | 当前组织允许的采纳动作及条件 | 指向明确的结果版本 |

界面应分别表达执行是否结束、质量检查状态以及人的决定。例如“已生成，2 项通过，1 项未检查”能让人理解当下情况。测试模型继续显式标记，其输出保留未验证状态。

现有采纳接口只允许 SUCCEEDED。可为尚未满足正式采纳条件的输出保留评价和修改入口，正式采纳继续遵守其服务端条件。这需要在文案和对象上明确，否则用户会把“我觉得有用”和“全部验收通过”混在一起。

**12.9 把不同的“继续”设计成不同的动作**

| 用户说法或操作 | 用户意图 | 应关联的对象 | 正确处理结果 |
| --- | --- | --- | --- |
| “第三点展开说说” | 继续讨论同一问题 | 当前会话和回复 | 新一轮答复，沿用可访问的必要上下文 |
| “把这份报告压缩到一页” | 修改既有产物 | 选中的产物版本 | 新修订与对应请求，旧版仍可核对 |
| “刚才断了，再试一次” | 恢复失败执行 | 失败请求和执行尝试 | 校验现状后创建新尝试，避免重做已成功的外部动作 |
| “再用新文件做一次” | 使用不同输入开展工作 | 原要求及新增资料 | 明确新的输入快照和结果归属 |
| “以后它都按这个格式写” | 改助手的长期行为 | 助手草稿或规则候选 | 显示差异和影响范围，按发布或规则机制生效 |
| “把这次做法给团队复用” | 提炼可复用流程 | 助手或技能草稿 | 由有权限的构建者审阅流程和授权后再发布 |

用户选择文字要求修改时，输入区显示目标段落或产物。发送后在这次修改下面展示进度，完成后标出新版本。用户可以比较版本并选择交付哪一版。只有重新生成的文件实际存在，才提供相应格式的下载。

修改旧用户消息会影响后续推理链，应明确生成新的工作分支或新会话，保留原记录。第一版可以先提供“复制要求，新建工作”，界面准确说明其后续行为。

一份报告在 Poros 内修改完成与写回 Kdocs 是两个有影响的动作。写回之前必须核对目标文档、账号、覆盖或新建方式及已有内容。任务取消也需要说明已落地的外部动作，用户能据此判断是否还要处理。

**12.10 从本次反馈形成长期规则**

| 步骤 | 用户操作 | 系统提供 | 下一状态 |
| --- | --- | --- | --- |
| 1 | 在具体结果上表达纠正 | 原要求、原结果与本次说明自动关联 | 本次反馈保存 |
| 2 | 明确选择“建议今后遵循” | 可理解的适用范围，默认为最小合理范围 | 进入规则候选编辑 |
| 3 | 填写或审阅规则 | 机械检查表单或语义要求，展示检查示例 | 草稿候选 |
| 4 | 提交 | 合法性、冲突和影响范围检查 | 待审，或指出需修订的冲突 |
| 5 | 独立审阅者处理 | 来源依据、受影响助手和版本、冲突说明 | 通过后形成明确生效修订 |
| 6 | 后续相关执行 | 展示实际注入的修订及本次检查 | PASS、FAIL 或 UNCHECKED 的真实证据 |
| 7 | 需要修订或停用 | 显示历史、提出人、审阅与使用记录 | 新修订或停用记录 |

候选规则的示例是规则设计样例，应明确由人编写或由模型建议。语义检查缺少有效 Judge 时显示未检查及原因。后续执行引用了规则，还需要有检查结果才能说明本次是否符合要求。

本次产物修改有自己的完成结果。长期规则是否通过审批，在单独的状态里呈现。用户可以继续处理眼前工作，也能回来查看规则建议的去向。

**12.11 构建者从想法到可用助手的完整路径**

| 步骤 | 开发者的决定 | 界面反馈 | 状态与后续 |
| --- | --- | --- | --- |
| 1. 描述用途 | 谁使用、做什么、使用什么材料、得到什么 | 用业务语言复述目标和输入输出 | 建立助手草稿 |
| 2. 明确范围 | 个人还是团队、适用项目、允许能力 | 给出可审阅的结构化配置 | 缺项逐项指出 |
| 3. 绑定能力 | 选择已登记工具、技能、知识和模型 | 展示来源、版本、账号需求、读写范围 | 配置保存且可追溯 |
| 4. 试用 | 输入代表性材料与要求 | 在草稿测试会话看到实际结果与执行过程 | 标注实际模型和环境 |
| 5. 定位问题 | 选中失败或不符合预期的回复 | 打开本次证据，并定位相关配置 | 修改草稿后重新测试 |
| 6. 提交发布 | 审阅版本说明、配置差异、权限变化、可用范围 | 冻结此次申请内容并显示等待状态 | 独立审阅 |
| 7. 发布生效 | 审阅者批准 | 当前线上版本、范围和使用入口明确 | 成员可按授权使用 |
| 8. 后续编辑 | 编辑下一版 | 显示“正在编辑草稿”与“当前线上版本” | 测试和发布仍关联各自版本 |
| 9. 拒绝或回滚 | 查看理由，选择修订或目标版本 | 显示实际目标、差异及资格校验 | 用记录可证明的版本继续工作 |

自然语言配置与结构化表单要操作同一份草稿。开发者说“以后输出 Markdown”时，应看到输出要求发生什么变化。普通用户使用助手时，则在该助手的已发布说明里理解产物能力。

测试面板至少需要说明测试的草稿修订、模型、资料、连接身份与工具授权。测试发起了真实写操作或实际外部调用时，沿用真实门控。只有读取样例协议的测试要直接标记。测试结果可以形成回归用例，发布前看到此次修订的相关验证情况。

发出发布申请后继续编辑，新的编辑属于下一份草稿。审批详情始终读取冻结申请。审阅者打开时发现范围已失效，应显示具体原因。拒绝要能带回原稿修改，旧版本相关能力已撤销时，回滚也要重新验证当前授权。

团队目录中的助手详情展示用途、负责人、使用材料、结果类型与开始示例。有编辑权限的成员看到“编辑助手”，有资格的审阅者看到审批入口。助手发布完成后，构建者可从同一个详情页亲自进入成员使用流程检查。

**12.12 团队协作、可见性和交接**

| 用户意图 | 界面必须说明 | 权限与状态约束 |
| --- | --- | --- |
| 把助手给同事用 | 授权使用者、可用范围、需要各自连接的服务 | 使用资格、编辑资格和个人连接分别校验 |
| 邀请同事维护助手 | 编辑的是哪份草稿，谁能发布和管理权限 | 并发修改出现冲突时保留各自修改内容 |
| 在项目里开展工作 | 项目成员能看到哪些任务和产物 | 采用并明确当前 Poros 项目 RBAC，不套用其他产品的隐私默认 |
| 分享结果链接 | 分享的是产物还是完整工作记录 | 接收者打开时按服务端权限验证来源和内容 |
| 交给同事继续 | 接收者能查看、评论还是发起后续执行 | 明确后续使用谁的连接、权限和费用归属 |
| 成员或能力被撤销 | 当前访问为何停止、如何联系负责人 | 后续查询与执行重新鉴权，历史范围按现有策略处理 |

项目分享、完整会话分享、产物分享和助手分享应分别显示实际受众。任何新增的分享能力都需要服务端权限和审计支撑。当前只有项目成员授权时，可以优先用项目范围内的受控协作，具体分享按钮取决于已实现的能力。

对并发编辑的取舍也需要明确。Dify 官方描述同一元素采用最后一次编辑，ChatGPT 助手文档则描述保存冲突提示。Poros 可以先采用可检测的草稿修订冲突，让第二位编辑者保留自己的文本并查看已有更新，再决定如何处理。这个选择应通过协作场景评审。[Dify 协作](https://docs.dify.ai/en/self-host/use-dify/build/workflow-collaboration) [ChatGPT 助手编辑冲突](https://help.openai.com/en/articles/20001143-chatgpt-workspace-agents-for-enterprise-and-business)

**13. 把状态和按钮放在一张表里检验**

下列状态是建议的用户可见语义。需要新增的等待、会话与产物修订数据，必须通过实现后的服务端契约提供。当前 Task 的 BLOCKED 可以结合审批记录显示等待审批，其他等待原因需要独立依据。

| 当前状态 | 主界面反馈 | 主动作 | 接受新消息的方式 | 退出与返回 |
| --- | --- | --- | --- | --- |
| 草稿 | 当前助手、范围、待发送要求 | 发送 | 继续编辑 | 保留草稿与材料 |
| 检查前置条件 | 正在核对资料和权限 | 等待或取消检查 | 编辑保留在草稿，清楚说明是否重做检查 | 原位置可恢复 |
| 缺少连接或材料 | 具体缺项 | 补齐所需项 | 保留要求 | 返回后重新验证 |
| 排队中 | 排队状态 | 取消 | 后续要求单独记录 | 依服务端状态恢复 |
| 执行中 | 当前步骤与已完成步骤 | 停止，查看过程 | 显示下一条的应用时机 | 不重复提交 |
| 等待用户输入 | 问题、选项或材料要求 | 提交回答 | 回答关联具体问题 | 直接回待答复项 |
| 等待独立审批 | 审阅事项、接收资格与进度 | 查看申请或取消 | 能补说明，变更受控内容需新申请 | 回到等待位置 |
| 界面连接中断 | 进度连接正在恢复 | 重新读取状态 | 暂存未发送内容 | 读取事件游标与当前记录 |
| 已生成且检查通过 | 产物、来源和通过项 | 查看、修改、按资格采纳 | 新请求关联产物 | 打开相同结果版本 |
| 已生成且检查未完成 | 产物、未检查原因 | 查看、修改、修复检查条件 | 反馈保留真实质量状态 | 提示未检查项 |
| 已生成但检查未通过 | 失败规则与受影响内容 | 修改结果 | 形成修订，重新检查 | 保留失败证据 |
| 执行失败 | 失败环节、已完成内容与恢复路径 | 修复条件或受控重试 | 明确新要求与重试的区别 | 不丢部分结果 |
| 正在取消 | 已收到取消请求，等待执行停下 | 查看进度 | 可暂存后续要求 | 以实际终态为准 |
| 已取消 | 实际停止位置与已落地影响 | 新建调整后的请求 | 新请求明确关联 | 仍能查到记录 |
| 无权继续 | 缺少访问或执行资格 | 按已有流程申请权限 | 保留用户自己的未发送输入 | 避免泄露受限内容 |

执行状态、质量状态和人工决定要各有数据来源。会话列表可以用一个清楚的摘要吸引用户打开，例如“需要您补一份资料”，详情中仍能看到具体执行状态。

**14. 常见失败如何恢复到原工作**

| 情况 | 提示要包含的信息 | 用户能采取的动作 | 重试之前必须确认 |
| --- | --- | --- | --- |
| 还没有可用助手 | 可用范围与负责人 | 选择已有助手，或由构建者创建 | 新助手已通过必要发布审批 |
| 模型凭证 401 | 哪个连接失效，密钥值不显示 | 原地更新并验证 | 正确的个人连接修订与模型绑定 |
| 403 或账户验证要求 | 供应商原始原因与处理入口 | 完成账号要求后重新测试 | 真实生成成功而非仅目录可读 |
| 429 | 触发限额的服务，已知时说明等待条件 | 等待后重试 | 不造成重复外部动作 |
| 503 或网络超时 | 失败步骤及已得到的内容 | 稍后重试，或选择已批准可用路径 | 外部动作是否已经落地 |
| 文档读取失败 | 指向具体文件与格式原因 | 替换、移除或补可读版本 | 所需输入已变化，需重新冻结 |
| 项目或文件权限被撤销 | 当前范围无法继续 | 联系负责人或用自己有权的材料新建工作 | 全部输入仍有访问资格 |
| 任务敏感操作被拒绝 | 拒绝原因和操作范围 | 修改方案，或结束 | 新申请与修改后的内容一致 |
| 审批无接收者或长期未处理 | 待处理人资格与等待情况 | 按组织规则分派、取消 | 当前审阅者有效且独立 |
| 提交网络中断 | 当前请求是否已经受理 | 查询状态，恢复原工作 | 幂等标识与原请求一致 |
| 执行中断但外部写入结果未知 | 哪一步的落地结果无法确认 | 查证外部状态，必要时人工处理 | 有证据避免重复写入 |
| 草稿保存发生冲突 | 谁的版本已保存与自己的未保存内容 | 查看差异、保留副本、重新提交 | 发布申请指向预期修订 |
| 更换模型需要新授权 | 受影响的助手与已发布绑定 | 由有权限者更新并审批 | 新执行使用的新版本已可用 |

Dify 的错误处理文档展示停止、默认值和失败分支等机制。对 Poros，错误本身及其恢复行为应明确呈现，备用路径必须在授权范围内。输出被缺失输入影响时，也要在结果里显示这一事实。[Dify 错误处理](https://docs.dify.ai/en/self-host/use-dify/build/predefined-error-handling-logic)

**15. 用具体工作逐步推演页面、对话和返回**

以下三段是设计情境，使用虚构的工作名称和文件名称进行纸面检查。没有据此执行真实业务或生成实际文件。

**15.1 成员用两份资料做简报，再修改结果**

| 步骤 | 用户操作或输入 | 界面反馈与位置 | 验证这个步骤的目的 |
| --- | --- | --- | --- |
| 1 | 登录后打开“资料分析助手” | 用途为分析材料并提供可追溯简报，说明实际支持的结果格式 | 用户能知道这个助手是否适合自己 |
| 2 | 输入“比较这两期销售情况，给经理写一页简报” | 要求保留在输入区 | 用户用业务语言表达目标 |
| 3 | 添加“二季度销售.xlsx”和“三季度销售.xlsx” | 两个文件各自显示存储和读取状态 | 用户能核对到底给了什么 |
| 4 | 选择“个人工作”，或从“季度复盘”项目进入 | 当前范围持续可见，项目进入时直接带入 | 可见性和资料范围明确 |
| 5 | 发送 | 校验条件，通过后显示已保存的请求与进度 | 受理和开始执行有各自事实 |
| 6 | 若资料包含多个无法判断的业务范围 | 助手只问“本次要看哪个区域”，给出实际发现的选项 | 追问针对决定性缺项 |
| 7 | 选择“华东” | 回答附在对应问题下，继续执行 | 回答接在同一项工作里 |
| 8 | 离开页面后从最近工作返回 | 回到该会话，显示当前真实阶段 | 返回不会重新提交 |
| 9 | 处理完成 | 一页简报、真实来源、结果格式与检查状态 | 结果可核对、可拿走 |
| 10 | 对第二段说“压缩，突出风险” | 显示正在修改哪份结果的哪一段 | 用户掌握修改对象 |
| 11 | 修改完成 | 新版本及变更说明，旧版仍可查看 | 修订沿用原工作，保留历史 |
| 12 | 下载当前版本，或按条件正式采纳 | 下载内容与当前选中版本一致 | 交付对象明确 |
| 13 | 用户额外选择“建议以后都用这一页结构” | 新建带来源的规则或助手改进候选，展示影响范围 | 长期复用经过明确意图和治理 |

这个情境检验了目录发现、文件准备、范围、持续会话、追问、后台运行、结果修订和规则建议。每一步都能在同一项工作内找到前后记录。

**15.2 构建者做一个可供同事使用的资料审阅助手**

| 步骤 | 用户操作 | 系统应如何响应 | 关键分支 |
| --- | --- | --- | --- |
| 1 | 从助手入口点创建，描述“帮团队检查文档是否符合我们的格式要求” | 生成可查看的用途、输入、输出和检查方式草稿 | 模型生成失败时保留原描述和实际错误 |
| 2 | 选择团队现有的格式文件 | 显示来源、范围与可读性 | 开发者有权查看，也要核对使用者需要的来源资格 |
| 3 | 选择模型和必要工具 | 展示固定模型绑定和能力来源 | 个人连接未验证时就地补齐 |
| 4 | 到草稿测试发送样例文档 | 展示测试环境、实际模型、读取与检查过程 | 涉及真实敏感能力时进入现有审批 |
| 5 | 选中某条不符合预期的结果 | 打开对应配置或检查证据 | 能发现是材料、指令、能力还是模型问题 |
| 6 | 修改输出要求并再次试用 | 配置差异与新测试记录关联 | 测试按当前草稿修订记录 |
| 7 | 提交发布 | 看到冻结配置、工具权限变化、受众和版本说明 | 后续编辑形成新的草稿状态 |
| 8 | 独立审阅者从待办打开 | 直接看此次申请、相关测试和权限差异 | 拒绝附理由，批准只作用于所审版本 |
| 9 | 发布生效后构建者点“使用” | 进入正式会话，显示已发布版本 | 与草稿测试有明确环境标记 |
| 10 | 同事从团队目录打开 | 只要求补齐自己实际缺少的条件 | 同事无法直接使用构建者的个人密钥 |
| 11 | 下一次编辑和发布 | 原使用者的运行保留原快照，新请求按策略使用新版本 | 使用者能看到版本变化 |
| 12 | 发现新版本问题，选择目标回滚 | 核对旧版本差异和当前授权后处理 | 已撤销能力不因回滚自动恢复 |

这个情境能判断“创建、测试、正式使用”的对象是否足够明确，也能判断独立审批是否审到了真实的版本。

**15.3 外部知识连接中断，原工作如何继续**

| 步骤 | 用户操作或系统事件 | 正确反馈 | 记录与恢复 |
| --- | --- | --- | --- |
| 1 | 用户要求“基于我授权的 Kdocs 材料整理会议要点” | 当前助手的可用来源与必要账号要求 | 先核对助手本身已具备对应能力 |
| 2 | 未连接 Kdocs | 在当前会话打开个人连接面板 | 用户要求和当前返回位置保留 |
| 3 | 账号验证通过 | 展示真实验证结果与可用范围 | 产生有效连接修订 |
| 4 | 实际查询中凭证失效 | 指向 Kdocs 的授权错误，显示已经完成的其他步骤 | 当前运行记录准确错误 |
| 5 | 用户重新授权 | 显示新修订与原请求状态 | 服务端重新检查原任务的冻结与审批要求 |
| 6 | 点击有效的恢复动作 | 显示将重试查询还是创建新尝试 | 避免让已完成的步骤产生重复外部影响 |
| 7 | 查询与整理成功 | 会议要点引用本次实际读取的资料 | 结果、来源和运行能互相定位 |
| 8 | 用户说“保存到 Kdocs 的某个文档” | 明确目标、写入方式和待保存内容 | 现有连接器具备相应能力时才提供执行，并走所需授权 |

最后一步检验能力名称与实际支持范围。若当前连接器仅支持检索与读取，界面可解释现有导出或人工保存方式。产品声称的能力应由真实可执行动作支撑。

**16. 这些流程需要怎样的页面衔接**

| 页面或区域 | 需要服务的决定 | 打开其他内容时的行为 | 返回时保持的内容 |
| --- | --- | --- | --- |
| 首页与最近工作 | 我要继续哪项工作、有没有待我处理 | 打开同一工作地址或待办对象 | 筛选、排序和未读定位 |
| 助手目录与详情 | 哪个助手适合我、是否可使用 | 使用进入会话，编辑进入草稿，发布记录就地查看 | 搜索条件与所选助手 |
| 工作会话 | 这次做什么、现在到哪一步、下一步需要谁 | 文件、来源和步骤详情优先在可关闭面板查看 | 未发输入、滚动位置、选定产物 |
| 产物预览 | 当前结果是否可用、哪里要修改 | 查看来源和版本，带目标内容发修改要求 | 当前版本与阅读位置 |
| 项目 | 哪些材料和工作属于这个背景 | 从材料发起工作时带入范围，返回有项目入口 | 项目筛选与资料选择 |
| 待办 | 我为什么需要介入、能决定什么 | 直接到具体申请或问题 | 已处理状态与剩余待办 |
| 构建页面 | 助手怎么配置、测试是否符合预期 | 测试在同一草稿背景里，证据针对选定请求 | 未发布修改与测试记录 |
| 个人连接面板 | 这次使用哪个账号、是否可用 | 原地授权与真实验证 | 返回原请求与缺项位置 |
| 组织配置 | 谁可用、谁维护、有哪些边界 | 按实际资格展示控制项 | 作用范围和保存状态 |

浏览器刷新应恢复到同一工作或助手。切换组织会改变资源范围，需要重新确认访问并为不同组织分别保存草稿。键盘操作、焦点回到原控件和错误提示位置要与当前动作对应。长列表加载、空列表和读取失败各有反馈。

这些区域可以映射到现有页面，布局通过后续原型验证。用户在每个区域都应能回答自己正在处理哪个对象、可做什么以及如何回到原工作。

**17. 复用现有实现的范围，以及真实新增依赖**

| 交互需求 | 当前可利用的基础 | 尚需明确或增加的契约 | 评审优先级 |
| --- | --- | --- | --- |
| 同一目标多轮沟通 | Task、Run、事件和已存输出 | 会话与消息归属、输入上下文、每轮处理范围 | 最高 |
| 在结果上修改 | 原输出、Artifact、文件及来源 | 目标产物修订、选区、结果版本与请求关联 | 最高 |
| 失败后恢复 | Worker、取消、限次重试、幂等 | 已完成外部动作的确认，按实际能力提供恢复 | 最高 |
| 多入口指向同一工作 | 现有项目、文件、任务读取 API | 稳定工作地址、返回位置与服务端权限 | 高 |
| 助手明确可用 | 发布版本、能力快照、modelPreflight | 明确的默认或指定助手，缺项与角色的恢复路径 | 高 |
| 文件直接开工 | 文件存储、预览和 TaskInput | 文件选择带入、范围提示、准备状态 | 高 |
| 当场连接服务 | 个人连接的保存、测试、修订 | 返回原工作、需要的连接与助手授权说明 | 高 |
| 本次反馈与长期规则 | 已有关联原运行的候选规则 | 独立的本次修改/评价对象，主动提升到规则 | 高 |
| 更细的动作审批 | 独立审批、冻结内容和审计 | 工具执行前的持久暂停、参数绑定和批准后恢复 | 后端专项 |
| 构建与使用连续 | 结构化 Builder、草稿测试与发布 | 开发与使用的明确状态、测试到配置的问题定位 | 高 |
| 并发维护助手 | 持久草稿与版本 | 保存时的修订冲突检测与修改保留 | 协作专项 |
| 分享完整工作或产物 | 当前项目 RBAC 与文件访问控制 | 若新增受众级分享，需单独对象权限及审计 | 按协作目标确定 |

当前 Task 和 Run 能描述一次请求及其尝试，形成持续会话和版本化产物需要额外的数据关系。具体实体名称和迁移方式由后续架构设计确定。前端可以在现有服务上改善入口、文案和返回关系，但持续会话、即时暂停恢复或动作级审批需要有对应后端行为。

模型和外部服务的真实性也属于流程前提。当前历史证据记录的供应商验证错误仍然是有效限制，需经新的真实测试才能改变验收判断。这份研究本身没有形成新的模型连通结论。

**18. 设计评审与用户走查怎样判定能否理解**

先用纸面流程检查对象和状态，再制作可点击原型，最后接真实业务验证。下面是建议的走查任务及通过证据，全部为待执行标准。

| 任务 | 观察内容 | 通过的可观察表现 |
| --- | --- | --- |
| 首次登录后开始工作 | 用户是否知道当前组织、可用助手与下一步 | 能找到真实可用入口，或准确说出缺少的条件 |
| 使用一个专业助手 | 是否理解用途和输入要求 | 自己选对助手并发出足够明确的请求 |
| 临时处理两份附件 | 是否被项目建档阻断 | 能在个人范围内完成材料准备 |
| 在项目文件上开始 | 是否需要重复选择项目和材料 | 发起界面已带入选定上下文，用户能核对 |
| 缺少个人连接 | 是否知道该配置谁的账号 | 原地配置、验证并回到原请求 |
| 执行中补信息 | 是否清楚新要求何时应用 | 能判断已收到、等待处理或已生效 |
| 离开再返回长任务 | 是否误以为任务停止或重新运行 | 打开原记录并准确理解当前状态 |
| 处理一个审批 | 是否了解要决定的内容和后果 | 从待办找到具体申请，能够解释批准范围 |
| 结果未检查 | 是否把完成执行理解为验收通过 | 能说清已生成、未检查和人的反馈状态 |
| 修改一段结果 | 是否被要求编辑助手或规则 | 修改针对该产物产生新版本 |
| 建议长期规则 | 是否知道作用范围和审批去向 | 能明确表达今后适用范围，并追踪候选状态 |
| 真实失败后恢复 | 是否丢材料或重复外部操作 | 修复原因后按明确的新尝试继续 |
| 构建并发布助手 | 是否区分草稿、测试和团队可用版本 | 从用途到正式使用完整走通 |
| 同事接续工作 | 是否理解可见性、账号与执行身份 | 看到明确范围，并在自己的资格内继续 |

走查要记录每次犹豫、返回、错误理解和需要提示的位置。可以计时和记录步骤数，但不能据纸面分析编造学习成本或效率提升数据。测试者应包括普通成员、构建者和独立审阅者。正式实现之后再验证安全与执行契约是否与原型一致。
