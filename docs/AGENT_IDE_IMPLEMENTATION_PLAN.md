日期：2026-11-25。基线：`ad8211c9`。状态：已获刘总“OK，按此方案开始改造执行”及“继续”的正式授权，正在实施；具体通过项和剩余项以实施记录为准。

本方案以刘总明确的“专门开发 Agent 的 AI IDE，左侧开发对话、右侧 PC/手机实时预览、统一设置”为当前实施依据。`AGENT_APP_PLATFORM_BLUEPRINT.md` 保留产品与交付背景；本文件明确改哪些、怎么改、按什么顺序验收，替代旧构想中优先扩大交付功能的排序。

## 1. 目标和范围

用户描述需求，AI 修改可检查的真实 Agent 工程，运行构建与选定测试，根据失败修复；右侧直接试用该版本。验收后的同一工程可生成独立软件，并接入免费额度内的远控通道。

整体分三个阶段，每阶段有完整可用结果：

1. **开发与预览**：真实工程、AI 开发链、双栏 UI、PC/手机试用。
2. **能力开发、装配与验收**：开发/运行模型分别绑定，定制开发技能与 MCP、复用已有能力、业务连接、轨迹与案例。
3. **软件交付与远控**：独立运行、具名安装、更新卸载、配对与跨网控制。

这三个阶段属于同一改造目标；第一阶段完成不能宣称已完成独立安装和公网远控。当前正在逐阶段实现与验证，第一阶段通过不代表全部交付已完成。

## 2. 主界面与交互

```text
┌──────────────────────────────────────────────────┐
│ 当前 Agent ▾                                设置 │
├────────────────────┬─────────────────────────────┤
│ 开发对话           │ 电脑 / 手机       预览状态   │
│                    │                             │
│ 描述需求、加材料   │ 正在开发的软件真实界面      │
│ AI 简短反馈进度    │ 可点击、输入、试用          │
│                    │                             │
│ 输入修改要求  发送 │                             │
└────────────────────┴─────────────────────────────┘
```

这是结构示意，不是成品截图。采用现有浅色与组件基础，双栏可拖动。主界面只常驻当前工程、开发对话、预览与设置。最近工程/新建/打开收在工程名称入口；代码、Diff、命令和轨迹按需展开。打包作为准备交付时的上下文动作出现。

### 2.1 核心流程

| 情境        | 用户操作                       | 系统反馈与后续                                       |
| ----------- | ------------------------------ | ---------------------------------------------------- |
| 首次进入    | 描述想开发的 Agent             | 建立工程；缺模型时原地打开对应设置，保留输入         |
| 正在开发    | 看简要进度，必要时停止         | 读取/修改/构建/测试有真实记录；停止不报告成功        |
| 构建成功    | 直接看右侧、输入试用           | 预览切换到明确的成功构建版本，试用记录独立保存       |
| 构建失败    | 在同一聊天查看原因与修复       | 失败诊断回到开发链；保留旧预览时明确标“上次成功版本” |
| 切电脑/手机 | 点击预览顶部设备切换           | 使用同一构建；不清空开发对话、输入或当前试用任务     |
| 提出修改    | 在左侧说明问题，可关联一次试用 | AI 基于工程和相应运行证据修改，构建通过才更新预览    |
| 修改设置    | 打开侧面板，保存后关闭         | 回到原位置；显示是否需重建/重新试跑，输入不丢失      |
| 准备交付    | 发出交付指令或选择打包         | 展示选定版本、验收结果、缺项和目标平台，生成真实产物 |

左侧命名“开发对话”，右侧命名“试用 Agent”。左侧修改软件，右侧执行软件。它们的上下文、会话和权限分别管理，试用输入不自动成为开发指令。

IDE 窄屏采用“开发/预览”切换，保留同一工程状态；右侧手机尺寸模拟与实体手机验收分别记录。

### 2.2 统一设置

设置采用 Radix 侧面板，按范围分组，不引入常驻管理导航：

- **开发环境**：开发 AI 的 API 地址、密钥、型号、真实连接测试。
- **当前 Agent**：运行模型/连接槽位、Kdocs/IMA/TinyFish 等账号、技能、MCP、必要的文件与操作权限。
- **交付设置**：进入第三阶段后按需提供软件身份、更新与远控配置。

技能支持添加/编辑内容、启停及范围说明；MCP 支持配置端点或受控运行方式、认证、连接测试、列出工具、明确授权后供当前 Agent 使用。界面分别显示“已保存”“连接已验证”“实际调用结果”，保存不视为验证通过。

设置负责配置和装配；技能/MCP 的实现通过当前开发对话编写和修改。用户可说“给这个 Agent 做一个技能”或“为这个 API 开发 MCP”；从当前工程入口也能单独新建 Skill/MCP 工程。开发目标以小标签明确显示，切换目标不另开一套 IDE。右侧默认保持 Agent 预览，定制能力时按需打开“能力测试”，关闭后返回原预览和试用状态。电脑/手机切换只作用于软件界面；技能和 MCP 采用适合其输入输出的测试面板。

开发模型与业务 Agent 模型分别绑定，可明确选择复用同一连接；不隐式使用开发者密钥发行。配置声明进入工程版本，密钥保存在加密凭证存储，通过引用使用。开发 AI 的 MCP 与业务 Agent 的 MCP 分清范围。

## 3. 技术路线与复用边界

继续使用 TypeScript、React、Radix、Tailwind、Fastify 和已验证的 DSH 执行边界。第一阶段不整体迁移 Theia/Code OSS；先完成已明确的轻量交互。通用代码编辑、Git 与终端按需接入成熟组件，SDK、工程和运行协议不依赖外壳。

| 当前实现                                   | 继续复用                             | 需要新增或调整                                           |
| ------------------------------------------ | ------------------------------------ | -------------------------------------------------------- |
| `web/src/App.tsx`                          | 登录和会话身份                       | 默认入口改为 IDE；已有业务入口做兼容访问，不继续占主导航 |
| `web/src/views/work.tsx`、结果与文件组件   | 消息、输入、文件、运行结果的部分组件 | 提取复用组件；开发会话和业务试用不共用一个语义模型       |
| `web/src/views/integrations.tsx`           | 四类连接保存、测试、断开             | 整理为统一设置侧面板，区分开发连接与 Agent 安装绑定      |
| `web/src/views/agents.tsx`                 | 精确授权及发布契约                   | 能力设置拆成小组件，去掉主流程中的长 Builder 表单        |
| `worker.ts`、`runner.ts`、`dsh-runtime.ts` | 任务、取消、超时、隔离、事件与审计   | 抽出运行适配；为开发工作区增加独立工具和执行策略         |
| `capabilities.ts`、连接器与模型桥          | 凭证代理、撤销、范围检查             | 支持工程工具与可携带绑定，按版本校验                     |
| `releases.ts`、Prisma                      | 不可变发布与版本校验                 | 源码/依赖/权限/验收关联到构建和发行                      |
| `storage.ts`                               | 受授权产物读写                       | 提取接口；独立 App 增加本地文件实现                      |

首先采用同库模块化，保留现有 API 和历史记录的权限语义。改变首页不删除已有业务数据，也不降低审批、撤权或跨组织边界。

## 4. 必须补齐的底座

### 4.1 真实工程与版本

Agent 工程包含源码、提示词、工具、Skill、MCP 声明、锁定依赖、权限/连接槽位、验收案例及发行配置。工作区文件和 Git 是源码依据，数据库保存索引、运行与发行证据。

建议增加明确的对象：

| 对象                        | 保存内容                                                                                                  |
| --------------------------- | --------------------------------------------------------------------------------------------------------- |
| AgentWorkspace              | 所有者、组织、工程定位、当前源码修订和最近成功构建；可包含 Agent/Skill/MCP 开发目标，能力工程也可独立打开 |
| SourceRevision              | 文件摘要/快照引用、依赖与配置摘要、可选 Git 提交                                                          |
| DevelopmentTurn             | 用户要求、请求 ID、修改前后修订、模型绑定、状态和执行记录                                                 |
| BuildArtifact               | 源码修订、SDK/运行版本、构建状态、诊断、预览与校验摘要                                                    |
| PreviewSession              | 固定构建、试用会话、环境绑定、运行与产物                                                                  |
| CapabilityPackage / Binding | 技能/MCP 源码与可分发实现、版本/摘要、依赖、验证记录，以及 Agent 对确切能力版本和范围的绑定               |
| AppRelease / Installation   | 第三阶段的软件包、签名、安装身份和更新记录                                                                |

这些是设计对象，实施时根据真实关系决定是否合并，避免为了表格创建冗余表。现有 `AgentProject` 仅是 Agent 与业务 Project 的关联，不作为已完成的源码工作区。

文件操作限定在授权工程根目录，检查路径穿越、符号链接和敏感文件。修改使用源码修订校验，遇到并发编辑返回冲突，保留用户已有改动。禁止把客户密钥加入工程或源码快照。

### 4.2 AI 开发链

```text
需求 + 当前工程 + 已选失败证据
  → 开发 AI 读取/检索
  → 生成并应用受校验的文件修改
  → 隔离环境构建与选定测试
  → 失败诊断返回 AI，有限次数修复
  → 成功构建绑定源码版本，更新预览
```

复用 DSH 引擎和工具 broker，增加受控的工作区读取、检索、修改及构建/测试工具。当前 DSH 默认关闭文件系统等入口，需要独立的开发执行策略；不能直接把宿主任意 Shell 和全盘访问交给 Agent。

构建工具、SDK 与基础模板固定版本。先支持一条 TypeScript 工程路线；新增第三方依赖需形成明确锁定记录。构建/测试运行在独立容器中，不在 API 宿主执行生成的代码。编译成功与测试通过分别记录，esbuild 转译不冒充 TypeScript 类型检查。

开发轮次可取消，重启时未完成轮次标中断并提供恢复动作。网络重试按请求 ID 找回原回执；不自动重放已经发生或结果不确定的外部副作用。自动修复限制次数、调用量和超时，失败后显示原因及保留工作。

### 4.3 Agent SDK 与运行

为 Agent、模型、工具、状态、产物和权限提供小而稳定的开发接口，先适配现有 DSH。IDE 试用和独立软件采用同一实现与运行契约，开发连接与客户连接分别绑定。

开发 AI 可以修改工程并执行获准构建；业务 Agent 只得到安装者授予的业务权限。SDK 与连接器从运行端获得经过校验的代理，密钥不注入生成的前端或 Agent 工程。

工具/MCP 调用记录真实输入、输出、耗时和失败，敏感信息脱敏。撤销连接或权限后，运行端重新校验，不只依赖启动时快照。

### 4.4 真实预览

生成的界面在受隔离的 iframe/独立来源中加载，采用沙箱、CSP 和经过校验的消息桥。它不能读取 IDE 登录态或直接调用平台管理 API。父页面和后端校验来源实例、构建、消息类型、权限与必要确认。

预览使用成功构建产物；右侧的输入通过运行协议进入真实 Agent。电脑/手机模式共用构建和试用状态。事件采用版本化结构、请求 ID 与游标，断线补发事件，不把补发等同于重新执行。

### 4.5 定制技能与 MCP：三类开发对象，共用一个 IDE

刘总新增明确需求：定制 Agent 时，技能和 MCP 本身也可能需要设计与开发。因此它们具有自己的源码、测试和版本，既可在某个 Agent 工程里开发，也可单独开发后复用；配置面板只负责绑定和管理。

| 对象       | 解决什么                                   | 定制开发的产物                                                    |
| ---------- | ------------------------------------------ | ----------------------------------------------------------------- |
| Agent      | 为用户完成一类工作，协调模型、能力和交互   | 业务实现、界面、状态、权限及验收案例                              |
| Skill      | 规定何时使用、处理步骤、业务判断和输出方法 | 标准 SKILL.md、必要参考/模板/脚本、依赖与验收案例                 |
| MCP Server | 向 Agent 提供标准化的系统接口              | 真实服务代码、工具输入/输出定义、认证适配、依赖锁、测试和运行配置 |

Skill 可以指导 Agent 使用 MCP 工具；同一个 MCP 可以被多个技能和 Agent 使用。不是每个技能都需要 MCP；已有工具或普通脚本已能完成的工作，不为了形式额外包装服务。

#### 4.5.1 技能开发链

1. 从业务需求、真实样例和已有能力判断是否需要独立技能，明确适用情况、处理步骤、输出要求与必要工具。
2. 优先查找可复用的本地/已授权技能，选择直接绑定、基于版本派生修改，或从零创建；保留来源与许可证。
3. 生成实际技能目录：至少 SKILL.md；按需要增加 references、assets、scripts。技能版本、权限要求与依赖摘要在 Poros 包清单中固定，不修改通用格式来冒充跨运行时保证。
4. 指令类技能由 Agent 在指定模型/环境中试跑；代码脚本先检查语法/类型，再在隔离环境实际执行。参考资料和脚本语言是否可用由运行端能力决定。
5. 以真实业务案例检查是否遵循判断与输出要求，保存失败证据并修改；至少覆盖一条不适用或边界情况，按技能类型选择精准验证。
6. 发布固定版本，再绑定到 Agent。后续修改形成新版本，既有 Agent 不静默跟随更新。

按 [Agent Skills 官方规范](https://agentskills.io/specification) 采用 SKILL.md 和可选目录。规范中的 allowed-tools 是实验性声明；最终权限仍由 Poros 运行端依据安装授权判断，技能正文不能自行扩大权限。标准格式通过不等同于业务效果通过。

当前仓库的 Skill 注册只保存 instruction 文本，运行时加载这段指令；尚无标准技能目录、脚本依赖、技能级验收和源码开发。迁移时保留旧指令的原始内容和授权引用，经显式版本转换后使用，不声称旧能力已经具备新功能。

#### 4.5.2 MCP 开发链

1. 读取真实系统/API 文档或已有实现，明确要暴露的工具、输入/输出、认证与读写范围；没有接口资料时标出缺口，不猜造端点。
2. 评估现有 MCP/连接器能否复用；需要新实现时，用实施时核对并锁定的官方 SDK 生成源码、锁定依赖和运行配置。
3. 优先打通 tools：工具发现、JSON Schema 参数校验、真实处理函数和错误结果。resources/prompts 依据实际需求提供，服务器只声明已经实现的协议能力。
4. 在受控环境启动服务，独立验证握手、工具发现、参数错误、实际调用、认证失效、超时与取消。外部写入需要明确授权和可用测试环境；协议夹具与真实业务联调分别记录。
5. 右侧按 schema 生成测试输入，显示结构化结果、错误与简要调用信息；原始协议详情折叠。可复用官方 MCP Inspector 的 CLI/测试方式，不直接向用户暴露其管理面作为业务接口。
6. 验证后固定源码/依赖/协议范围/工具清单，再绑定到 Agent。工具清单或权限发生变化时重新检查绑定，升级不自动获取新增权限。

优先复用 [MCP 服务开发资料](https://modelcontextprotocol.io/docs/develop/build-server)、[Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) 和 [Inspector](https://modelcontextprotocol.io/docs/tools/inspector)。实现时再次核对 SDK/协议版本并协商兼容范围，不因使用某份旧版示例就宣称兼容全部当前规范。

当前仓库 MCP 主要为固定 Kdocs 连接器。新增可定制服务必须有真实处理函数、协议客户端/服务端、认证、测试和发行依赖，不能只保存一个 URL 或配置 JSON 就算完成 MCP 开发。stdio 服务在隔离运行环境启动，Streamable HTTP 通过受授权网络适配访问。

#### 4.5.3 装配、版本和分发

开发 AI 可以在同一对话中协调修改 Agent、技能和 MCP，并显示本次涉及的对象。共用工程读取/修改/构建/诊断机制，分别采用技能验证、协议验证和 Agent 场景验证，不复制三套开发引擎。

每次 Agent 构建固定实际技能/MCP 版本、内容摘要和工具授权，并形成依赖锁。开发环境和客户安装环境分别绑定真实账号。独立安装包包含允许分发的技能文件和自带 MCP 实现，或明确外部 MCP 的配置要求；不能假设客户机器存在开发者本地命令、缓存路径或凭证。

本地能力优先满足当前工程，再支持导出/导入给其他工程复用。共享版本保持不可变；客户专有规则、数据和账号与通用实现分别核对，不能自动复制到其他客户。

#### 4.5.4 一条必须验收的定制链

以“售后工单助手”为拟议样板：创建业务判断/报告技能，基于真实 API 开发工单查询 MCP；先分别验证技能和 MCP，再让 Agent 组合使用；修复一条失败案例；最后在独立安装环境重新绑定账号，运行同一验收案例。以上为待实施的验收剧本，当前没有创建样板代码或完成任何调用。

能力级验证通过与 Agent 组合验证通过分别记录。缺少真实 API/凭证时，可以完成代码和受控协议测试，但该 MCP 的真实业务验收保持待验证。

## 5. 分阶段最小任务与完成标准

以下是拟议实施位置，不表示文件已经创建。每单元完成立即运行其对应验证，失败先修复，再进入依赖项。

## 6. 独立安装和免费远控的约束

桌面软件首版优先 Electron/React/Node 复用，底层仍保留现有 PostgreSQL/DSH 语义，公共组件可共享，各 App 数据和凭证隔离。安装器自动准备受支持运行环境；WSL/管理员/重启要求和体积必须实测后说明。不能因为想做轻量界面就绕过执行隔离，或未经验证宣称可直接切换 SQLite。

远控优先验证 Cloudflare Workers + SQLite Durable Objects 的出站 WebSocket 中继；有现成域名可使用正式 Tunnel。免费额度按账号共享，额度耗尽时远程明确不可用、本地仍可用，不自动付费。Quick Tunnel 临时地址且不支持 SSE，仅适合演示/诊断。来源与详细限制见背景方案第7节。

手机首版是配套 PWA 远程客户端。原生 APK/IPA、宿主桌面控制属于分别构建和验收的能力，不能把 PWA 或普通转发包装成已具备这些功能。

## 7. 验证策略

- 工程/API：按修改范围验证真实文件、版本冲突、身份边界、取消、连接变更和事件恢复。权限/运行底座变更后运行相关既有负向回归，最终再做必要整体检查。
- 构建：服务端/UI 类型检查、受影响 lint、Agent 工程类型/构建/选定验收案例。避免只验证 IDE 自己能编译。
- 浏览器：后台 headless，1366×768 和1920×1080；手机预览390px及 IDE 窄屏。覆盖初次开发、修改、构建失败、旧版标识、两类对话分离、设置往返、刷新恢复和能力变更。
- 运行隔离：预览不能取得 IDE token；生成代码不能访问宿主资源；两个软件实例的数据与凭证不交叉。
- 定制能力：技能格式/内容与实际效果分别验证，MCP 协议与真实业务分别验证；单个能力通过后，还须检查 Agent 组合使用、精确版本绑定和安装后的依赖可用性。
- 真实供应商：使用已授权的真实连接。协议夹具用于可复现边界测试，明确标识，不能代替实际模型或供应商验收。
- 安装/远控：在真实支持环境安装，并以实际跨网设备验证。浏览器模拟尺寸不作为实体手机或公网验收。

仅运行对应测试，失败修复后复测；通过后不无理由反复扩大。最终审计需求覆盖、真实实现、测试证据、失败修复、权限、交付物、外部限制及残余事项。
